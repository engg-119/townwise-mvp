# Town research live eval, 2026-11-19

The live eval of D66 town research (OpenSpec change `town-research-agent`, design decision 18, tasks 10.1 and 10.2), run once before research ships to production. It decides the ship gate ([CONFIRM: the live eval's ship gate]) and whether `TOWNWISE_RESEARCH_WEB_FETCH` is worth turning on.

**Verdict: the gate passed on every criterion** (shipping config: town threads with web fetch off, the merge as fixed below). Web fetch showed no recall or grounding gain, so `TOWNWISE_RESEARCH_WEB_FETCH` stays false.

| Gate criterion | Threshold | Measured | Result |
|---|---|---|---|
| Event recall, curated rows in the window | at least 0.5, with `n` | 0.667 (2 of 3, `n` = 3) | pass |
| Precision, hand-labeled sample of 30 stored rows | at least 80% | 90% (27 of 30; the 3 others could not be opened) | pass |
| Source validity | 1.0 | 1.0 (42 of 42 stored sources) | pass |
| Duplicates among stored rows | at most 10% | events 7.7% (3 of 39), entities 8.3% (2 of 24) | pass |
| Town threads empty or failed | at most 1 of 6 | 0 of 6 | pass |
| The competitors thread counted in the precision sample | yes | 2 competitor rows sampled | yes |

## How it ran

- Script: `api/scripts/research-eval.ts` (guard, probes, arguments) and `api/scripts/research-eval-full.ts` (the threads, the merge and the scores). Each thread runs through the product's own executor (`research/call.ts` `runThread`) and each run is merged with the product's own `research/merge.ts` `planMerge`.
- Town: Hanover, NH. Window: 2026-11-19 to 2027-05-18 (today plus 180 days; the curated calendar runs to 2028-06-11, so no cap applied).
- Held out: no curated row in the prompt's `known` list and no curated source URL as a seed, so every curated row the research found, it found on its own.
- Groups: the six town threads with web fetch off (the shipping config), the six again with web fetch on, and one `neighborhood` and one `competitors` thread for a public Hanover restaurant that is not a Townwise customer (named here only by its type: a downtown restaurant and bakery), with `TOWNWISE_RESEARCH_PLACES_TO_AI` false, so the restaurant was named by its own name and town as an owner would type it, and no Google content was sent.
- Key: the dev `ANTHROPIC_API_KEY` from the main checkout's `api/.env.local`, loaded into the process environment only. `NODE_ENV` was not production.
- Spend control: a thread starts only while money spent, plus the reservations in flight, plus its own reservation stays under `--max-usd` (25, then 20 for the rerun). No thread was skipped.
- Runs: run 1 at the branch head (57ff0ba0 plus the eval script), then two fixes (below), then run 2 with the same arguments. The precision sample and the gate use run 2, rescored with the merge fix (the merge is deterministic over the saved findings, so the rescore is exactly the merge the product would make).

Command (run 2):

```sh
TOWNWISE_RESEARCH_EVAL=1 node scripts/research-eval.ts --no-probes --restaurant "<the restaurant's name>" \
  --redact "<its name>" --max-usd 20 --concurrency 3 --sample 30 --record --save-runs <runs.json> --out <results.json>
```

## Fixes the eval drove, before and after

1. **Dates quoted from the wrong words** (`research/prompt.ts`, commit cd368d7a). Run 1 grounded only 24 of 52 town findings. Of the 28 ungrounded: 7 had a `dateQuote` copied from the gather's own sentence instead of the cited words, 3 of 113 quotes across all threads held a JSON-escaped line break (`\n` copied literally from the extract input, so the quote matched no page), and most others quoted cited words that held no date (a page heading). Fixes: the extract input collapses the cited words' whitespace, the extract is told to copy `dateQuote` from inside a cited quote of the event's own sources, and the gather is told to write each date in the sentence that cites it. Tests: `test/research-prompt.test.ts` (3 new).
2. **A curated term restated by another thread** (`research/merge.ts`, commit e2a1ae3e). Run 2's tourism thread stored "Dartmouth Fall Term Final Examinations" (Nov 20 to 25) over the curated "Fall term finals", since the term-day rule read only the `schools` thread and the titles share 2 of 6 words. The rule now also drops a `school` finding of any thread on a curated term's first or last day. Test: `test/research-merge.test.ts` (1 new). `design.md` decision 8 and the `research-findings` spec delta updated.

## Calibration (design decisions 5 and 7)

- **Tokens a search** (`SEARCH_TOKENS`, from `usage.iterations`: each iteration's whole input less the previous iteration's input and output, over the searches, on threads with no fetch): run 2 mean 6,309 over 39 searches, per thread 4,646 to 8,392; run 1 mean 6,359 over 37, per thread 5,013 to 7,782. One single-search thread reached 8,392 (5% over 8,000). `SEARCH_TOKENS` stays 8,000: it is a ceiling that the formula multiplies by every iteration, and the whole reservation stays 12 or more times the measured cost (below).
- **`char_location` `document_index`**: one run 1 thread fetched 2 pages; its 5 `char_location` citations all carried `document_index` 1, and each cited text was found in the second fetched page, the page the ledger maps index 1 to. With the probe's single fetch at index 0, the mapping (the page's position among the fetch results) holds; index 0 with two fetches was not observed. No other thread cited a fetched page.
- **`pause_turn`**: none in 28 gather calls plus the probes, so a continuation's billing is still unmeasured. The executor's continuation path stays covered by the scripted tests only.
- **Extract bounds**: largest extract output 3,487 tokens (of 12,000). Largest extract input 9,446 tokens against bounds of 22,645 to 45,096. The ledger's share (input less the gather's output) was at most 3,351 tokens a search or fetch made, under `LEDGER_TOKENS_PER_CALL` = 4,000.

## What this eval does not show

- Recall rests on 3 curated event rows. The miss is the same in every run: the sports thread found basketball and hockey home games but never the last home football game (Nov 21, two days after the run).
- One run per configuration: threads vary run to run (run 2's sports thread made 1 search, run 1's made 2; term recall moved from 4/4 to 3/4).
- The location run stored 6 rows, half of them low confidence, and the competitors thread (with Google names not allowed) found events at one competing venue only.
- A researched holiday with a different title than the curated one ("MLK Jr. Day") is stored beside it; the dedupe rule needs half the title words.
- Precision checks dates only, not whether a happening matters to a restaurant.
