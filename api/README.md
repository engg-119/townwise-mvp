# api

Townwise backend: one Node process (`src/main.ts`) composed from the kit modules in `kit/` (copied from camkeith/modules; versions in `../KIT.md`). Sign-in is Google only.

It mounts three routers. The kit’s `/auth` handles sign-in, sessions and two-step sign-in. `/lab` (`src/lab/callback.ts`) holds the forecast lab job’s two callback routes (see Forecast lab). Townwise’s `/api` (`src/app.ts`, routes in `src/access/routes.ts`) handles access, the Places search, organizations, locations, sales data, notes, the tuning chat, the team and the staff console. No kit file is changed; all Townwise code is under `api/`. "The build spec" and "spec Section N" in this README and in code comments mean `../docs/portal/spec.md`.

## Run locally

Needs Node 24 (`nvm use` reads `.nvmrc`) and Docker. From the repo root:

```sh
nvm use
npm install
docker compose up -d    # Mongo on 27017, Valkey (Redis) on 6379, Azurite (blobs) on 10000; stop a local mongod first if 27017 is taken
grep -v -E '^AUTH_(JWT|ENCRYPTION)_KEYS=' api/.env.example > api/.env.local
printf 'AUTH_JWT_KEYS=k1:%s\nAUTH_ENCRYPTION_KEYS=e1:%s\n' "$(openssl rand -base64 32)" "$(openssl rand -base64 32)" >> api/.env.local
npm run dev -w @townwise/api
curl localhost:8080/healthz
```

`api/.env.local` is gitignored and holds throwaway local keys, plus the production secrets developers read from Key Vault (the Places keys and the calendar key, `../infra/README.md` steps 17 and 21). Never commit it or paste its values.

Townwise staff are the addresses in `TOWNWISE_SUPERADMIN_EMAILS` (comma-separated, at most 20). Production refuses an empty list. A staff account must turn on two-step sign-in, and every staff request needs a session that passed a code within the last 60 minutes. In development `TOWNWISE_STAFF_TWO_STEP` is `off` unless set to `required`: staff then need no authenticator, and `staff.verifiedUntil` runs 60 minutes from each request. Tests default to `required`, and production refuses `off` at boot.

Google sign-in needs an OAuth web client (Google Cloud console, APIs & Services, Credentials, OAuth client ID, type Web) with `http://localhost:8081` as an authorized JavaScript origin. Put its client ID in `AUTH_GOOGLE_CLIENT_IDS`. Without it, `/auth/google` answers 404.

Google calendars (Owner calendars, item 9) are off locally until `TOWNWISE_GOOGLE_CALENDAR_CLIENT_ID` (that web client’s id), `TOWNWISE_GOOGLE_CALENDAR_CLIENT_SECRET` and `TOWNWISE_CALENDAR_KEY` are all in `api/.env.local`. Never change the production Google Cloud project’s publishing status for a local run: it is the whole project’s, sign-in’s included. Use a separate development project (its web client’s id in `AUTH_GOOGLE_CLIENT_IDS` too, the Google Calendar API enabled, the two read-only calendar scopes on its consent screen) whose consent screen is in Testing with you as a test user (its grants last 7 days), or a web client in the production project, which stays “In production”, accepting Google’s unverified-app screen (`../infra/README.md`, step 22).

Email (see Email, under Flows) is off locally while `EMAIL_ENDPOINT` is empty. Local sending works on macOS and Linux only: the API starts `az` without a shell, and Windows' `az.cmd` needs one. To send from your machine, run `az login` with an account that is Owner of, or holds `Townwise email sender` on, the Communication Services resource, then set `EMAIL_ENDPOINT=https://acs-townwise-2d2c15bf.unitedstates.communication.azure.com` and `EMAIL_SENDER=no-reply@townwise.tech` in `api/.env.local`. With no managed identity outside production, the API takes its token from `az account get-access-token` (`src/azure-identity.ts`). The emails really send, from the production sender to the address you sign in with, and their links go to `TOWNWISE_WEB_URL`. A failed token shows as `townwise.email_failed` with code `token`: run `az login` again.

## Check

`npm run verify` from the repo root runs `npm ls`, lint, typecheck and every kit module's unit and integration tests (Docker required).

The api's own tests run with them (`npm test -w @townwise/api`; integration tests start Mongo and Valkey in Docker through testcontainers). `npm run test:unit -w @townwise/api` and `npm run test:int -w @townwise/api` run each half.

Rules behind the matrix:

- An organization always keeps at least one active org admin. Demoting, removing or leaving as the last one answers 409 `last_admin` and changes nothing, for org admins and staff alike, even when several of these run at once. A removal (leaving included) recounts when the seat was an org admin, or was being demoted at that moment: a demotion marks the seat (`demotingSince`) in the same write and clears the mark once its own recount or revert is done. So a member can leave, and staff can remove a member from, an organization with no active admin yet (staff created it and its admin hasn’t joined, or its approval found the requester seated elsewhere). A role change or removal of an invitation never counts, since it takes no active admin away. One exception: when the person took a seat in another organization before theirs could be put back, the removal stands and is answered as done.
- A staff address never resolves as a member, even when an organization invites it, because the staff check runs first.
- Staff see client sales figures and note text only through view-as, or by opening an organization as its admin (Open as admin), before or after anyone joins it. Otherwise member routes answer staff with 403 `no_access`. [CONFIRM: staff see values only through view-as]
- Removing someone does not sign them out. Their next member request answers 403 `no_access`, and `GET /api/me` says `removed`. [CONFIRM: no session revoke on removal] Staff can sign a person out on every device from People, which revokes every kit session and leaves their seat alone.
- Every staff action on an organization (its name, status, team, setup writes, each view-as, and each opening as admin) is recorded before it takes effect, and that organization’s admins read it as Townwise staff activity. Changes staff make while open as admin are recorded after they take effect, as an org admin’s are. [CONFIRM: show staff activity to org admins, with staff emails]
- One active organization per person, enforced by a unique index. Invitations are per organization, so two organizations may invite the same address, and no add result depends on another organization. [CONFIRM: one organization per person; per-organization invitations]

### Access states

`resolveAccess` (`src/access/resolve.ts`) decides who the caller is on every request, from the primary, in this order. It never writes, and nothing is cached. `GET /api/me` returns the result as `access`, for the client to route on `access.state`.

| `access.state` | When |
|---|---|
| `staff` | the current email is in `TOWNWISE_SUPERADMIN_EMAILS`, two-step sign-in is on, and this session passed a code at sign-in no more than 60 minutes ago |
| `staff_setup_required` | a staff address without two-step sign-in |
| `staff_reauth_required` | a staff session created before two-step sign-in was turned on (`session_before_codes`), or more than 60 minutes old (`session_too_old`) |
| `member` | an active seat in an active organization, with `org` and `role` |
| `org_suspended` | an active seat in a suspended organization |
| `invited` | open invitations for the current email in active organizations, each naming who added it; `pendingRequest` is set when the person also has a pending request |
| `pending` | a pending access request |
| `rejected`, `removed` | the newer of the latest rejected request and the latest removed seat; `removed.byYou` is true when the person removed themself |
| `no_org` | none of the above |

A signed-in person whose kit user no longer exists gets 401 `unauthenticated`. That is the only 401 Townwise code answers; every other denial is 403 or 404, because the client refreshes its session on any 401.

## Flows

### Sign-in

1. Google sign-in goes through the kit’s `/auth/google`. There is no sign-up step: the kit creates the user on first sign-in. The kit also mounts magic-link routes, but `src/email.ts` rejects every send, so `POST /auth/magic-link` answers 503 `email_unavailable`.
2. `GET /api/me` then answers the person’s access state. The portal pages that route on it (Waiting, No access, Joining, Request access and the rest) are not in this branch.

### Joining with an email an admin added

1. An org admin adds addresses (`POST /api/org/members`). Each becomes an invitation in that organization. Townwise sends no email for invitations; its only emails are the two in Email below (spec D14).
2. When that person continues with Google, `GET /api/me` answers `invited`, listing each invitation with the organization, the role and who added it.
3. `POST /api/me/join { inviteId }` claims the invitation by compare-and-set. It matches the invitation, the caller’s current email and an active organization, then withdraws any pending request of the caller. A second organization answers 409 `already_in_org`. `POST /api/me/decline { inviteId }` deletes the invitation instead.
4. The server never joins on a GET. The build spec has the client’s Joining page call join as soon as it loads, when there is one invitation and no pending request. [CONFIRM: auto-join without a click]

### Requesting access and approval

1. A person in `no_org`, `rejected` or `removed` sends `POST /api/access-requests`: organization name, their name and role, the town, the number of locations, an optional note and an optional list of checked Google places (`places`). Each person has at most one pending request. Their state becomes `pending`.
2. Staff validate the person by hand, outside Townwise, for example by matching the email domain to the restaurant or by phone. [CONFIRM: what “validated manually” means]
3. Approve (`POST /api/admin/requests/:requestId/approve`) creates the organization, its locations: one per checked place (D24), or one in the requested town, and the requester’s org admin seat. A retry completes the work. If the requester is deleted while it runs (their request goes with them), the approval takes back what it made for them and answers 404 (Deletion). [CONFIRM: first location at approval] [CONFIRM: a request keeps the place the requester picked; staff check it by hand]
4. Reject (`POST /api/admin/requests/:requestId/reject`) stores an optional message of up to 500 characters, which the requester sees. They may send a new request. [CONFIRM: rejected people may request again]
5. The requester sees the result at their next `GET /api/me`. While they have not seen it and the organization has no sales day, that answer also carries `welcome: { firstName, restaurant }` for the welcome statement (`../docs/portal/spec.md` 15.8): `firstName` is the first word of the name on their request, or null for an honorific (`Mr`, `Mrs`, `Ms`, `Mx`, `Dr`, `Prof`), an initial or a word over 40 characters; `restaurant` is the organization’s current name. The client records that it showed it with `POST /api/me/welcome`, and from then on `welcome` is null on every device. Invited teammates, admins of organizations staff created, and staff in view-as never get one. [CONFIRM: welcome for the requester only]

### Email

Townwise sends two emails (spec D14), each only to the person it concerns, from `no-reply@townwise.tech` through Azure Communication Services:

| Email | When | To |
|---|---|---|
| Request received | `POST /api/access-requests` stored the request and its `access_request.created` (201) | the caller’s current address |
| You’re in | the approval call that inserts the requester’s admin seat, after `member.joined` | the requester’s current address, read at the start of that call |

- Nothing else sends email: invitations, staff-created organizations, joins, rejections, removals, view-as and deletion send none, and the kit’s magic-link route still answers 503. A 400, 403, 409 or 429 sends nothing, and so do an approval retry that finds the seat already there, a losing concurrent approval and an approval undone by the requester’s deletion.
- The send is queued after the write and the response does not wait for it. A failure never fails, delays or retries the action: it is logged and the email is lost. So is a send still in flight when the process stops (the shutdown drain waits 2 seconds).
- The words are in `src/mail/templates.ts` and the layout in `src/mail/layout.ts`: fixed subjects, no greeting by name, no images or tracking (`userEngagementTrackingDisabled` on every message), and links only to `TOWNWISE_WEB_URL`. An email carries the organization’s name, its town and the address the person signs in with, never a figure, a file or a note. Reply-To is `TOWNWISE_EMAIL_REPLY_TO` when it is set.
- `src/mail/acs.ts` calls Email - Send (`2023-03-31`) over `fetch` with an Entra token for `https://communication.azure.com` from the managed identity (`src/azure-identity.ts`: the user-assigned identity named by `AZURE_CLIENT_ID`, cached until 5 minutes before it expires). Outside production, with `IDENTITY_ENDPOINT` and `IDENTITY_HEADER` unset, the token comes from the developer’s `az login` instead (Run locally), cached the same way; a failure there carries a fixed message, never the CLI’s output. Access keys are disabled on the resource. Any refusal drops the cached token.
- On in production from the 2026-11-09 release (`../infra/README.md`, step 9). Off while `EMAIL_ENDPOINT` is unset, as it is locally unless you set it. Nothing about a send is stored, and it writes no audit event.

### Places search

The access request can start by finding the business on Google Places (New). The API calls Google Places itself, so the search goes only to the API. The exceptions are the maps (the checklist's map of every checked place, D29, and the confirm card's), images the browser loads straight from Google (below), which is why the web CSP's `img-src` allows `https://maps.googleapis.com`.

- Off until `GOOGLE_PLACES_API_KEY` is set: autocomplete and details answer 503 `places_unavailable` to every request, and the client shows the manual fields. Google failing, or not answering within 5 seconds, also answers 503 `places_unavailable`.
- The client sends `POST /api/places/autocomplete` as the person types (debounced, 2 characters or more), then `POST /api/places/details` for the suggestion they pick, or for each place they check. Both carry the same session token, a version 4 UUID the API issues on the search's first autocomplete; Google bills the typing and the pick as one session. A details call ends the session whose token it carries. A checked place after the first in one list carries none, and the server sends Google a new token, so the next autocomplete starts a new session. Without a token, autocomplete makes one and returns it, for the client to send from then on. The server checks only the token's format and keeps no record of it.
- Autocomplete asks Google for US results in English, with no type filter, and answers up to 5 place suggestions (`name` is Google's main text, `detail` its secondary text, such as "Hanover, NH, USA"). D29: each suggestion's `kind` comes from Google's types: `business` for `establishment` or `point_of_interest` (and for a prediction without types, so nothing unclassified is lost), `address` for `street_address`, `premise` or `subpremise` (an exact address, for a business Google does not list); anything else (a town, county, street without a number, postal code, neighborhood or plus code) is dropped, so whatever is checked is a business or an exact address. [CONFIRM: suggestion kinds read from Google's types; towns, streets and postal codes are not offered]
- D29: autocomplete also sends Google a `locationBias` rectangle from 40.4, -80.6 to 47.5, -66.9, State College, PA to Bar Harbor, ME with margin (`SEARCH_BIAS` in `src/places/google.ts`). Without it Google biases by the caller's IP, which is the API's data center, not the person. It is a bias, not a restriction: a business elsewhere in the US is still found by its name. It sends Google a fixed region, nothing about the person. [CONFIRM: the search leans toward the Northeast, where the twelve researched towns are]
- Details asks for the place's id, formatted address and address components only (`X-Goog-FieldMask: id,formattedAddress,addressComponents`). `address` is for display; the client keeps the name from the suggestion it picked.
- `town` is a `TownInput` the access request accepts unchanged. It is one of the twelve researched towns when the locality, postal town, sublocality or `administrative_area_level_3` (town or township) matches one by name and state, ignoring case, or when any of them is an alias: Lake Placid, NY is `north-elba-ny` and North Conway, NH is `conway-nh`. Otherwise it is `{ townId: null, name, state }`, named by the first of those components. It is null when the place is outside the 50 states and DC (a territory included: its country component is not `US`, or its state is not in the fixed list), or has no usable town name.
- Details also answers `map`: a Google Maps Static image of the place with a mint pin, as `{ url, width: 640, height: 320 }` (drawn at scale 2, 1280 by 640 pixels; the client sizes it by the 2:1 ratio), in the mode the body's `theme` names: `'light'` a light map with the light palette's mint pin (`0x136a53`), `'dark'` or none the dark map with the dark mint (`0x7bd2b4`), byte for byte the URL a client from before light mode gets. Both modes send the same parameters in the same order and hide points of interest, icons and transit; only the colors differ (`STATIC_MAP_STYLES` and `STATIC_MAP_PIN` in `src/places/static-map.ts`). `url` is a `https://maps.googleapis.com/maps/api/staticmap` URL for Google's current id of the place, signed by the API with `GOOGLE_MAPS_SIGNING_SECRET` (`src/places/static-map.ts`), and the browser or the native app loads it from Google, which sees the viewer's IP address. The API never fetches, relays or keeps the image. The URL holds `GOOGLE_MAPS_STATIC_KEY`, a key of its own restricted to the Maps Static API with unsigned requests refused (`../infra/README.md`, step 17), so the key alone draws nothing. `map` is null while the map is off (either variable unset); a map URL is never made unsigned. Signing is local, so the map never fails or delays the answer.
- D29: `POST /api/places/map` signs one map of every checked place, `{ placeIds, theme? }` (1 to 25 distinct ids, and the mode as on details) to `{ map }`, the same `{ url, width: 640, height: 320 }` or null while the map is off. One id is exactly details' map (centered on the place at zoom 15); several leave out `center` and `zoom`, so Google fits every pin, and send one `markers` parameter with a mint pin per id in the order given. 25 ids at the 512-character maximum make a URL of about 14,400 characters in either mode, under Google's 16,384 (`test/places-map.test.ts` works it out). D47: `labeled: true` letters each pin, A for the first id sent: one `markers` parameter per id (`color|label:A|place_id:…`), with one id still centered at zoom 15; 25 ids at the maximum make 15,289 characters with Google's 39-character key, still under the cap (`test/places-map.test.ts`). Settings sends it for its map of every location; the checklist never does. The checklist sends the portal's mode (always dark on native) and asks again when it switches. It never calls Google, so it answers with the Places search off, and it stores, logs and audits nothing: no id, no count, no URL.
- Nothing from these routes is stored. The typed text, place ids, addresses, Google's answers and the signed map URL never reach a log or an audit event; a Google failure logs `townwise.places_failed` with the route id and a code. [CONFIRM: the town matching rules, which are not yet checked against live Google answers]
- Places unit: the client offers the search in three places, and only while it is on: the access request (P3, Steps 1 and 2 on one screen, D29), Add location (P10) and a location's settings (P16, "Name and place" leading the page, D47). Before P3 shows it, the client sends autocomplete an empty body, which answers 503 `places_unavailable` while the search is off and 400 `invalid_request` while it is on, with no call to Google (pinned by `test/places-off.int.test.ts` and `test/places.int.test.ts`); P10 and P16 read `placeSearch` from `GET /api/org` instead. Under view-as the client sends neither. A location keeps Google's id for the place the org admin confirmed and the town read from its address (see Organization and locations). On P3 the request keeps each checked place's Google id, its name cut to 80 characters, its town (D24, spec 6.3) and its kind (D29), and the first checked business's name fills in Organization name until the person types in it (a street address never does). Wherever the checklist shows (P3, P10, P9's first location, P21's staff setup), one map of every checked place sits above the checked rows (`POST /api/places/map`). On P10 the name only seeds each row's Name field ("{Google name}, {Town}", or "{Organization name}, {Town}" for a street address, D29; while the organization has no location, a single checked place has no Name and is sent with that default), and the location keeps Google's id and the town. The address, the suggestions, the typed text and the map are never kept.

### Team

- An org admin adds up to 20 addresses at once, with a role (default member). [CONFIRM: role chosen at invite, default member] Each address is normalized as the kit does (trimmed, lowercased) and gets one result: `invited`, `already_invited`, `already_member` or `invalid`.
- An organization holds at most 200 people, active and invited (409 `member_limit`).
- Changing a role or removing someone uses change, recount, revert, so a demotion or removal never leaves an organization without an active admin, even when two run at once. A demotion recounts when the row was an active seat at its write, and marks the row until it is done, so a removal of that seat meanwhile recounts too; its revert matches the row by id, organization and the role it set, whatever its status, so a seat removed meanwhile gets its admin role back and that removal, finding no active admin, puts the seat back.
- Removing an invitation deletes it. Removing a member keeps the row as `removed`, for history and for the `removed` state. Removing a member, or leaving, also ends their Google calendar access in the organization, their Google calendars leaving its locations (Owner calendars, item 9).
- Anyone with a seat leaves with `POST /api/org/leave {}`, from Settings. It is a removal of oneself (`removed.byYou` is true), recorded as `member.left`. The body must be exactly `{}`.
- Staff edit any organization’s team from its console page (`/api/admin/orgs/:orgId/members`), with the same outcomes, caps and last-admin rule. Rows they add carry `addedByStaff`, which Team shows as added by Townwise staff.

### Staff organizations

1. `POST /api/admin/orgs { name, adminEmail, id? }` creates an active organization with no location and an `org_admin` invitation for that address, added by staff. That person joins as admin the next time they continue with Google. `id` is an optional 24-hex id the client generates once per new organization and sends again on a retry: a repeat answers 200 with the organization it made and writes no second `org.created`. It counts as a repeat only for an active organization this route made (no request) with the same name, whose team holds the same admin address, or nobody yet; any other organization with that `id` is 409 `conflict`. A repeat adds nothing, except the admin invitation when the organization has nobody yet (a create that stopped before it), and that invitation’s `member.invited` is written before it, as for a staff team edit. Two repeats racing past the check make one organization; the loser’s `org.created` is followed by `staff_action.not_applied` (`conflict`). [CONFIRM: staff can create organizations without a request]
2. `PATCH /api/admin/orgs/:orgId { name?, status? }` renames, suspends or reactivates. A value that already holds records nothing. Suspension keeps every record: members resolve to `org_suspended`, every member route answers them 403 `no_access`, and invitations into it are hidden. Reactivation restores access with no other step.
3. Each of these, each staff team edit and each setup write (below) writes its audit event before the change. A request with several changes (a name and a status, or several addresses) writes all its events first and then makes its changes in one write, so a refused event (503) never follows an applied change; an event already written when a later one is refused is followed by `staff_action.not_applied` (`unavailable`). The organization’s admins see all of them, and every view-as of their team, on `GET /api/org/staff-activity`.

### Staff setup

While an organization is active and nobody has ever held a seat in it (open invitations don’t count), staff add, rename and delete its locations and upload or delete their daily totals from the console, so the first admin who joins finds a populated page. Staff use it with a real client’s data only with that client’s consent. [CONFIRM: staff can add locations and upload daily totals for an organization nobody has joined yet; write-only; ends at the first join; used only with the client's consent]

1. The five routes are under `/api/admin/orgs/:orgId/locations` (Staff console). Each has policy `staff`, scopes through `scopeForStaffOrg` (404 for an unknown organization), then answers 409 `org_not_in_setup` while the organization is suspended and once anyone has ever joined it, then runs the org admin route’s own checks (`src/handlers/locations.ts`, `src/handlers/sales.ts`): the same bodies, limits and error codes, the town checked, and a place id checked with Google on the staff member’s own `townwise:places` budget. A location of another organization is 404.
2. Then the staff event is written (Audit and logs) and the org route’s write runs. A staff upload replaces the days it covers, as an org admin’s does. A name another location already has is 409 `location_name_taken` after the event; so are a location deleted meanwhile (404) and stored files off while the location has some (503 `files_unavailable`); each is followed by `staff_action.not_applied`.
3. These routes are write-only. Answers carry ids, names, towns, counts and date coverage, never a figure. To read, staff open the organization as its admin (Open as admin), or, once someone has joined, use view-as.
4. Locations and uploads made here hold the staff member’s user id in `createdBy` and `uploadedBy`, with `byStaff: true`. Every view that names an uploader (`GET .../sales`, `GET .../sales/history`, and the upload’s own answer) shows “Townwise staff”, never the staff email.
5. Setup is checked before the event, with no lock. A join that lands between the check and the write is accepted: the write is recorded, and the new admin sees it in their staff activity.
6. It never reopens. A join (`POST /api/me/join`) and an approval set the organization’s `firstJoinedAt` right after the seat write, only while it is unset, and nothing clears it, so an organization whose people all left, were removed and were deleted stays closed: it belongs to a former client, with no admin left to see a staff write. ### Stored files and the file reader

The other way in for sales history (spec 11A): a person drops their exports as they are, and Townwise reads them on the server. Off until `FILES_BLOB_ACCOUNT_URL` is set (every route below answers 503 `files_unavailable`), so the browser upload above stays as the fallback and as the choice to send only daily totals. [CONFIRM: every cap and limit below]

1. **Upload, in chunks.** `POST /files { name, sizeBytes, purpose: 'history' | 'reference' }` (a `reference` file joins no import; see Your data below) opens an upload session in the location's active import (one per location; the first drop creates it, `open`) and answers with the caps (`limits`). The browser sends each 8 MiB chunk as `PUT /files/:fileId/chunks/:index` with an exact `Content-Length`; the API streams it through a hashing Transform into Azure's Put Block, so no request holds a file, and a dropped connection retries one chunk. `POST /files/:fileId/complete` commits the chunks, tells the kind from the extension and first bytes, and drops a second copy of a file already stored for the location (409 `file_duplicate`). Caps: 200 MiB a file, 50 files an import, 500 a location, 10 uploading at once in a location, 5 GiB stored and 2 GiB uploaded a UTC day per organization. An upload session past its 24 hours counts toward none of them. A replica takes 12 chunk streams at once; the 13th answers 503 `uploads_busy` with `Retry-After: 2`.
2. **No file is refused for its type.** CSV, TSV and text files, Excel workbooks (.xlsx, .xlsm), PDFs, Word documents (.docx) and ZIP archives are read. Old Excel (.xls) and Word (.doc), Numbers files, password-protected Office files, images and anything else are kept and say why.
3. **Read my history.** `POST /imports/:importId/start` queues every stored file; files that complete later are queued too. The file reader runs in each API replica (`src/files/worker.ts`): it claims the oldest started import under a 90-second lease (renewed every 30 seconds, taken over when a replica stops), reads its files one at a time in upload order, and skips a suspended organization's. Each file is read in a worker thread with 192 MiB of heap and 20 minutes; past either it is kept as `too_complex`, and the API carries on. Text is streamed twice (the first pass finds the header row under any title block, profiles every column and proves the date order; the second adds rows up per date), in UTF-8, UTF-16 or windows-1252.
4. **Rules first, then the person.** The reader's column logic is the browser's (`src/files/parse/` ports `client/src/portal/upload/`, held to the same fixtures), with longer header guess lists [CONFIRM: header guesses]. What the rules cannot settle (two date columns, an unproven date order, which columns are guests and net sales, which location value is this location, what one row is) becomes one question on the import, whose options are header names or the location column's values, never other cells. The import waits; `POST /imports/:importId/answer { questionId, choice }` stores the answer on the file and reads it again, and "not sure" keeps it as `needs_help`.
   - **AI for columns, only when the rules find no guests or net sales column.** With `ANTHROPIC_API_KEY` set, the reader asks Claude Opus 5.5 (`src/files/extract/`) to name them from a redacted profile: header text (40 characters at most), each column's kind of value and rough shape, and up to 15 rows of value tokens such as `<int>` or `<text>`. Never a row, a figure, a file name, a ZIP entry path or the restaurant's name. A confident choice is applied (reported as `ai`), an unsure one is suggested in the question. Each answer is saved on the file, so a re-read after a later question reuses it without another call. At most 2 calls a file, 5 a ZIP, 20 an import, and `TOWNWISE_FILES_MONTHLY_BUDGET_USD` an organization a month (`tw_files_usage`); off, spent or failed, the person is asked.
   - **PDFs** are read with `unpdf` in the worker thread (no fonts loaded, nothing rendered): a table starts at a line holding a date header and a guests or net sales header, its column bands come from those headers' positions, and a "total" line ends it. **Word** tables (`w:tbl`) are read with `saxen`. Text outside tables is never read into a row.
   - **ZIP archives** are read in place by ranged reads (never downloaded whole), after guards on the central directory: 20,000 entries, 2 GiB declared, 100 to 1, no overlapping entries, a ZIP inside a ZIP opened up to 50 MiB and none deeper; an entry that inflates past its declared size distrusts the whole archive. Each entry is a file of its own, listed in `tw_file_entries` with what became of it. Tables with the same header are one family, decided once and added up together; when two families cover the same days, only the higher-ranked one counts.
5. **Days, a cleaned copy and a report.** A read file's days go through the same store and rules as the browser upload: an org admin's replace the days they cover, a member's add new days only. Each file has one `tw_uploads` record (kept on the file, so a retry reuses it), a cleaned copy (`date,guests,net_sales`) and a report: header names, the header row, which rule or answer decided each column, row and day counts, skipped rows by number, and dates. The report holds no data cell except the location value chosen.
6. **Status and time left.** `GET /imports/:importId` (polled) shows each file's status and outcome, its progress in the current phase, and `etaSeconds`: measured, never guessed, and null ("Estimating") until three seconds and five percent in, until a file of the import has finished (for queued files), and while the import waits for a turn.
7. **Downloads and deletion.** The original streams back to its uploader and the organization's admins (in 32 MiB parts for large files), the cleaned copy to every member, both as attachments the API never serves inline (on the web, Your data’s item page draws one in the browser, D28). Deleting the original keeps the cleaned copy, the report and the days, and replaces the stored name with the kind (and a ZIP's entry paths with nothing). Deleting a file removes the original, the cleaned copy, its entry list and the record; its days stay. An org admin can delete every sales file's original at a location at once (`DELETE /originals`, Your data's "Delete all originals for this location"); items kept for reference stay whole (D28), because their original is the whole item. Deleting a location's sales data deletes its stored files; a location with files cannot be deleted before that; an organization's deletion deletes all of them (Deletion). Under view-as, names and entry paths are null, nothing downloads, and every write is refused.
8. **Retention** [CONFIRM: retention periods]. A daily sweep (`src/files/sweeper.ts`, one replica a day under a lease) discards upload sessions after 24 hours, deletes originals a year after upload (a file never read is kept unread as `raw_deleted`), deletes files dropped but never sent for reading after 30 days, finishes staff purges of flagged files, drops daily upload counters after 3 days, and deletes blobs whose record is gone once they are a day old.

Not in this build (spec 11A.8): reading `.xls` and `.doc`, reading notes or free text in sales files (except in a file someone lets TownwiseAI read, Your data 7), and any upload purpose but `history` and `reference` (D28). Stored files stay off in production until the client pieces, the drop screen and the privacy page ship with them (`../infra/README.md`, step 18).

9. **Undo** (`DELETE .../data/:ref/ai`). The person who asked or an org admin removes what the read made: the notes carrying the file as their source (one the person since edited too), its upload with the days that upload still holds (through the upload delete: only days it added, since it never replaced one; days a later upload replaced stay), and its summary item (an edit of it too). ### Notes (the tuning step)

- A note belongs to one location. Its kind is closure, private event, opening or other. It covers a date range of up to 366 days, optionally only certain weekdays, with an effect (closed, more guests, fewer guests, unknown), optional expected guests and a detail of up to 280 characters (required for other). [CONFIRM: notes first, AI chat later]
- A note may carry local hours, `startTime` and `endTime` (`HH:MM`, 24-hour): both or neither, start before end on the same day, none on a closure. [CONFIRM: an event with hours ends by midnight on its own day] Hours are informational: uploads are daily totals, so a timed event changes the day's total and shows its hours in the reason.
- A buyout is a private event with effect closed. It may carry expected guests (the party's size); every other closed note may not.
- Authors edit and delete their own notes; org admins edit and delete any. [CONFIRM: author or admin]
- Notes adjust the published forecast on read, from the town's today on (spec 14.5, D30, `src/forecasts/adjust.ts`): a private event with more guests and a guest count adds its guests to the day's range, a buyout books the day, a closure closes it, and any other note is listed with why it changed nothing. Runs are never rewritten, so an edit or delete shows on the next read. The tuning chat (its `list_notes` and `get_day` tools, as data), TownwiseAI’s questions (which days a note explains) and the forecast lab's input (three flags per day) read notes too. The detail text never reaches a log, an audit event or a forecast reason.
- A note TownwiseAI made from an event in a file someone let it read (Your data 8) carries `source: { via: 'ai_file', fileId }` in `tw_notes` and in the note's view (null on every other note), with the person who asked as author. ### Owner calendars

A location’s own calendars (openspec change `connect-owner-calendar`; owner decision, 2026-11-12, GitHub issue #10), each an imported `.ics` file, a subscription link (Google Calendar’s secret iCal address, Outlook, Apple or a booking system’s feed), or a Google calendar connected by signing in with Google (openspec change `connect-google-calendar`, spec D39; item 9). [CONFIRM: 5 calendars per location, a 60 character name, a 6 hour refresh, 12 link adds an hour, 1 MB and 2,000 events a calendar]

1. **What is kept.** A location holds at most 5 calendars of every kind (409 `calendar_limit`; each takes one of 5 slots under a unique index, so adds at once cannot pass it), each with a name of 1 to 60 characters from whoever adds a file or a link, or from Google for a Google calendar (item 9), whose events are kept by item 9’s rules: each instance of a repeating event, the events ahead first. `src/calendar/ics.ts` parses a calendar on the server in the location’s town (its today and time zone, `src/time-zones.ts`): single events from 400 days before the town’s today to 400 days after, at most 2,000 a calendar, the first by start. A repeating event (RRULE or RDATE) is counted (`skippedRepeating`), not imported; its moved instances and canceled events are left out. A UTC time is read as the town’s wall time, and an event keeps its hours only when it starts and ends on one date or ends by 06:00 the next morning (a late night, its start day’s). An event keeps its UID, its title (cut at 200 characters), its start and end dates (the end included) and its hours; its description, location, attendees and organizer are never read. A calendar file is at most 1 MB of its own text (400 `too_large`), and only its events are kept, not the file. Anything that is not a calendar is 400 `not_calendar`.
2. **A link is a secret.** Its address grants read access to the whole calendar, so it is sealed with AES-256-GCM under `TOWNWISE_CALENDAR_KEY` (`src/calendar/secret.ts`, a fresh IV each time) before it is stored, opened only to fetch it, and never answered, logged or audited; a link shows as its name and host (`calendar.google.com`). Without the key, adding or refreshing a link answers 503 `calendar_links_unavailable` and the refresh loop does not start, while files still import. A link sealed under another key (the key was changed) fails each refresh with `key_mismatch` until it is added again; its events stay. A Google calendar’s id and its connection’s refresh token are sealed the same way (item 9), so changing the key breaks every Google connection too.
3. **Fetching.** `src/calendar/fetch.ts` fetches only `https:` on port 443 with no user name or password (`webcal:` is read as `https:`; anything else is 400 `bad_link`). It resolves the host and fetches nothing (400 `blocked_address`) when any address it resolves to is loopback, private, CGNAT, link-local (the managed-identity endpoint included), multicast, documentation or reserved, in IPv4 or IPv6 (an IPv4-mapped address is judged by its IPv4 address), then connects only to the address it checked, so a second DNS answer cannot swap it. It follows at most 3 redirects by hand, each checked the same way, has 10 seconds for the whole fetch (`timeout`), reads at most 1 MB (`too_large`), sends no cookies and names itself `Townwise calendar reader`. The other failures are `unreachable` and `http_error` (a status other than 2xx, or a redirect with no Location or past the third). Adding a link spends one of the account’s 12 link adds an hour (`townwise:calendar-links`, Rate limits), then fetches and parses it before anything is stored: a failure refuses the add with its code. A Google add spends one of the same 12, the account’s adds that fetch (item 9).
4. **Replacing events, with no transaction.** A refresh reserves a new generation on the calendar, writes the new events under it, switches the calendar to it with a compare-and-set on the generation it started from, then deletes the older generations’ events. Reads return each calendar’s current generation, so a reader sees the old events or the new ones, never a mix, and rows a crash left behind go with the next refresh or the removal. A failed refresh keeps the last good events and records its code as the calendar’s `status`.
5. **The refresh loop** (`src/calendar/refresher.ts`) runs in each API replica while `TOWNWISE_CALENDAR_KEY` is set, shaped like the file reader (deps in, start, drain). 30 seconds after start and then every 15 minutes, it claims due links and Google calendars together, one at a time across organizations, the longest due first (`claimDueCalendar` in `src/stores/cross-tenant.ts`: one compare-and-set takes a 5-minute lease, so each due calendar is read by one replica), and refreshes each through the calendar store under `scopeForCalendarRefresh`; a Google calendar is read through `readGoogleSource` (item 9). A success is next due 6 hours later; a failure 6 hours after the first in a row and 24 hours after two or more. A suspended organization’s calendar is not read and is looked at again in 6 hours, and a calendar whose location is gone is removed with its events (a Google calendar’s connection marked for a check first). Then it claims due Google connection checks one at a time, under the same 5-minute lease (`claimDueGoogleConnection`, scoped by `scopeForGoogleCheck`, which only `access/policy.ts` mints): a person with no seat in the organization ends the access (`seat_gone`); a seat removed less than a minute ago is left due (`unsettled`, nothing written), since a removal refused as the last admin puts it back; a connection backing no calendar a day or more after its connect ends (`unused`); any other is checked again 24 hours on (an unused one younger than a day, at a day after its connect), set only while no mark came in during the check (`releaseCheck`, a compare-and-set on the `checkAt` it claimed). The lease is 5 minutes for every claim, calendars and connection checks alike: a Google read is at worst a token call and 8 event pages of 10 seconds each, plus writing 2,000 events, and ending access adds a revoke of 10 seconds. At shutdown the loop drops a link fetch in flight and aborts every Google call in flight (its lease runs out, and a later look refreshes the calendar or checks the connection) and waits for its writes. ### Ordering

The next order from each of a location's suppliers, built from the location's own ordering setup, item sales and counts (`src/orders/`; the design is `../openspec/changes/complete-bar-ordering/design.md`; the build spec is `../docs/portal/spec.md` P30, P31 and D35). Nothing is sent to a distributor.

1. **The setup** (`tw_order_setups`) is one document per location: up to 20 suppliers, each with 1 to 7 deliveries (a delivery weekday, an order-by weekday and an order-by time, HH:MM in the town's zone, one delivery per weekday), and up to 300 items, each with a supplier of the setup, a category (`bottles_cans`, `draft`, `liquor` or `cocktail_ingredient`), a unit (`cases`, `kegs`, `bottles` or `units`), servings per unit (0.1 to 2,000), a par (0 to 999), a deal size (1 to 999, or none), a never-run-out flag and up to 10 point-of-sale names, each with the servings one sale uses (greater than 0, at most 50). It is saved whole by `PUT` under compare-and-set on `version`: the first save sends `expectedVersion: 0` and inserts version 1 (a unique `{ orgId, locationId }` index catches a racing insert), and a stale `expectedVersion` is 409 `setup_changed`. The server mints a 24-hex id for each supplier and item sent without one; a new supplier names itself to its items by a `key`, which the server swaps for the minted id. Every member edits the setup. [CONFIRM: every member may edit the ordering setup]
2. **Item sales** (`tw_item_sales`) are one document per location and business date, holding the servings each setup item sold that day, keyed by item id. The browser reads the point-of-sale export, matches each item name (trimmed, case-folded) to the setup's point-of-sale names and sends `{ from, to, days: [{ date, items: { [itemId]: servings } }] }`, so a name that matched nothing never leaves the browser. A range is at most 31 days, starts on or after 2010-01-01 and ends before the town's today (today is still open, so its sales are not all in; a range ending today or later is 400 `invalid_request`); each sent date lies in the range and is unique; a day holds at most 500 items with 0 to 100,000 servings each. Every item id must belong to the setup (400 `unknown_item`). The upload rule follows the sales upload's (D16). An org admin's upload (staff opened as admin included) replaces: the server upserts every sent day, then deletes the stored days of `[from, to]` that were not sent, so a retry completes it; two such uploads over overlapping ranges at once are not merged: each day holds whichever wrote it last. A member's upload adds only the sent days not already stored: a stored day stays exactly as it was (one sent with no items is not zeroed), nothing is deleted, and the answer counts the days left alone as `kept`. So only an org admin replaces or clears item sales, by upload or by delete. A stored day is covered: an item absent from it sold none that day. A day not stored is unknown. Every member uploads; only an org admin deletes. [CONFIRM: members upload item sales, org admins delete them] [CONFIRM: members add only item-sales days not already stored; org admins replace]
3. **Counts** (`tw_order_counts`) are one document per location and count date: the quantity on hand of each item counted that day, in purchase units. A count is dated from 14 days before the town's today through today and holds 1 to 300 items of the setup (400 `unknown_item`) with 0 to 9,999 in steps of 0.5. A save sets each sent item and keeps the items counted earlier that day. An item's latest count is the newest date holding it; the board and the setup page read the last 400 days, since a count older than 7 days still sets the quantity (the par less what it counted).
4. **The board** (`GET .../orders`, `src/orders/live.ts`) reads the setup, the last 244 days of item sales (the oldest past window's delivery 26 weeks back, its order-by up to 6 days before that, and the 8 weeks of weekday means before its order-by), the latest counts, the published guest forecast for today and the next 30 days (the window the forecast route reads), the last 8 weeks of the location's guests and the saved edits for deliveries from today on, runs the engine (`src/orders/engine.ts`, a port of the core of `../reorder/reorder/engine.py`) and applies the owner's saved edits and rules. It answers one order per supplier that has a delivery and an item, by cutoff. Without a setup, or with one that has no supplier delivery or no item, it answers `{ available: false, reason, missing }`. A board's `missing` names `item sales` (no covered day in the last 8 weeks) and `a recent count` (no item counted in the last 7 days). Every answer carries `today`, the town's date, which the page's count and upload use. Reading it writes nothing and logs nothing. `?sample=true` answers a labeled preview in the same shape (`sample: true`, every line at its par with no deal size and no other deal option, ordered by the next Wednesday 2:00pm not yet passed), which no edit or rule can be saved against.
5. **How a line is computed.** The window runs from the order-by date through the day before the supplier's following delivery. Daily demand is the item's mean servings for that weekday over the covered days of the last 8 weeks, times a guest index (the forecast guests over the location's own mean guests for that weekday in the same 8 weeks) on the open days a published forecast covers; a day it marks closed expects no sales, and a booked day (a private buyout) keeps the weekday mean with no index. An item that no covered day of the 8 weeks sold has no mean, so it follows the par at low confidence. The window's demand `mu` is their sum, in purchase units after the category's loss (bottles and cans 1%, draft 12%, liquor 5%, cocktail ingredients 0%). `sigma` is the sample standard deviation of past windows' misses (null under 2 windows). The order-up-to level is `mu` plus `z` times `sigma` (or 0), with a target chance of not running out of 98% for a never-run-out item, else 95% for bottles, cans and draft, 92% for liquor and 88% for cocktail ingredients. With no count the quantity is the par; with a count older than 7 days it is the par less what was counted; otherwise it is what the level needs beyond what is on hand (never under the par less what is on hand), rounded to a multiple of the deal size by cost with the par swap, or up to a whole unit when the item has no deal size (a deal size of 1 is the same). A draft item's par is one higher when the window uses more than one unit (one tapped, one backup, and a second backup; `engine.py` `draft_backup_par`), at most 999, and the line's `par` is that one (`setupPar` is the owner's). A line holds at most 999; a quantity above it is 999, and the why line says so and that it may fall short, claiming no chance of not running out and no coverage of the expected use. The why line says the par set the quantity when it did (never a chance of not running out then), asks for a count only for a count 3 or more days old, and says the history is short when under 28 days of item sales made the line medium. Confidence is low with no count, a count over 7 days old or no item sales; medium with a count 3 to 7 days old or under 28 covered days; else high. The deviations from the Python engine are Decision 5 of the design. [CONFIRM: targets, loss rates, 8 weeks, the guest index, whole units, count and confidence thresholds]
6. **Edits and rules.** `POST .../orders/decisions` saves the owner's quantity for one line of a supplier's next order, found on the live board at that moment (the recommended quantity is the board's, never the caller's), with a reason of 1 to 280 characters. An edit or a rule saved in another unit than the item's unit now (the setup changed it) is not shown or applied; remembering the same reason from a new edit moves that rule, if it is on, to the new edit's amount and unit (compare-and-set on the old unit, recorded as `order.rule_saved`). ### Forecast lab

The build contract is spec D27, 14.4 and 10.15 (`../docs/portal/spec.md`); the job is `../modeling/lab`. - **The callback.** The job holds the API URL and the calibration id, and no secret: it signs in with its managed identity (`src/lab/caller.ts`). Before each call it asks Entra for a token for the lab callback app (a credential-free app registration in bootstrap) as the lab identity, and the API checks the token’s RS256 signature against the tenant’s keys, its issuer (`https://login.microsoftonline.com/{TOWNWISE_LAB_TENANT_ID}/v2.0`), audience (`TOWNWISE_LAB_AUDIENCE`), tenant and caller (`oid` equal to `TOWNWISE_LAB_CALLER_ID`, the lab identity’s principal id). A second fetch, by anyone, is 404. Whoever fetches first gets the result token, so code running as the lab identity that fetches another calibration’s input first can read it and post a forged result for it (published if its scorecard passes the gate and that organization’s forecasts are on), and the calibration’s own job finds its fetch refused: a known risk the owner deferred (`../infra/README.md`, Known risks). ### Active days

Which days each member used the app, for the staff Overview (openspec change `staff-overview`, spec D48 and 6.30). [CONFIRM: Townwise keeps the dates on which each signed-in person used the app, for 180 days]

1. **When it is written.** The route chain (`authorize` in `src/access/routes.ts`) calls the recorder (`src/access/activity.ts`) once a request has passed its policy, right after `recordResolution`, never inside `resolveAccess`, which stays a pure read. It records only a `member` principal with a seat (`memberId` set), not in view-as and not open as admin: a member or org admin on their own seat in an active organization. Staff, staff in view-as (whose principal carries the target's id), staff opened as admin, and people with no seat, a pending request or a suspended organization are never recorded; a request refused by its policy writes nothing, and one that passed it but was then refused by its body parser or route limiter still counts. `GET /api/me`, read on every app load, counts, so opening the app is a day. This is the one exception to "a GET never writes" (spec 7.3): a member's first request of a UTC day writes one row, on a GET too.
2. **What is kept.** One document per person, organization and UTC day (`utcDay`): `{ _id: "<orgId>:<userId>:<YYYY-MM-DD>", orgId, userId, day }`, nothing else. The `_id` is built from the three, so not even the time of the first request is kept (an ObjectId would carry it). No path, route, page, IP address, device or count.
3. **At most once per person per day per replica.** Each replica keeps the `<orgId>:<userId>:<day>` keys it has written today and clears them when the UTC day changes; a key already there returns at once, otherwise it upserts `$setOnInsert`, and a duplicate key from a race is success. The write is not awaited, so it never delays or fails the request; a failure logs `townwise.activity_write_failed { orgId, code }` and drops its key, so the person's next request that day tries again.
4. **180 days.** The first write of each UTC day in each replica also deletes every row dated before the 180 days kept (today and the 179 before), not awaited, logging `townwise.activity_days_removed { deleted }` or `townwise.activity_days_remove_failed { code }`. It needs no stored files and no worker; a day with no activity at all only delays removal to the next active day.
5. **Deletion.** An organization's deletion deletes its rows, in both sweeps; a person's deletion deletes theirs in every organization (Deletion). A member removed from an organization keeps their rows there until they age out (owner, 2026-11-17).
6. **Who sees it.** Staff only, as counts by organization and day on the Overview (`GET /api/admin/overview`); never a list of people. In an organization of one person, its count is that person's use, which the privacy page says.

## Endpoints

Every route is JSON under `/api` and runs one chain, built from the table in `src/access/routes.ts`:

1. The kit’s `requireAuth` (401 `unauthenticated`).
2. The `townwise:writes` limiter, for every method but GET, before anything is read.
3. `resolveAccess`.
4. The view-as guard, then the open-as-admin guard (Open as admin): End passes; a staff route answers 409 `open_as_admin_active`; a route not marked `openAsAdmin` answers 403 `open_as_admin_refused`.
5. The route’s policy.
6. The body parser: 32 KB (the Places map's included), 2 KB on Places autocomplete and details, the files JSON routes and the order edit, rule and card routes (1 KB on a rule’s turn-off), 256 KB on the upload routes (the member one, item sales and staff setup’s), 1 MB on the ordering setup’s save (300 items with 10 point-of-sale names each can pass 256 KB), 2 MB on adding an owner calendar (a calendar file of at most 1 MB, as a JSON string), or 8 MB on reading the ordering setup with TownwiseAI; none on GET and DELETE. It runs after the policy, so a refused request is never parsed. On the setup read alone, the route's `beforeBody` step runs right before the parser: it holds this replica's byte gate for the body's `Content-Length` (413 `payload_too_large` without one or over 8 MiB, 503 `extract_busy` when the gate is full; Ordering 9), and `assertRouteTable` refuses the step on any other route. The chunk route has no parser: its handler streams the raw body after the policy passed, and a refused chunk's connection is closed unread.
7. The route’s own limiter, if it has one.
8. The handler.

Policies:

- `signed_in`: anyone signed in.
- `member`: an active seat in an active organization; anyone else gets 403 `no_access`.
- `org_admin`: a member whose role is `org_admin`; a member gets 403 `forbidden`, anyone else 403 `no_access`.
- `staff`: a staff address that passes the two-step gate. A staff address that fails it gets 403 `staff_setup_required` or `staff_reauth_required`; anyone else gets 403 `forbidden`.
- `staff_self`: the signed-in staff member’s own gate, which also passes during view-as and while open as admin. Only view-as End uses it.

Member routes take the organization from the caller’s own seat, or in open as admin from the grant, never from the request (`PATCH /api/org` and `POST /api/org/locations` only compare an `orgId` with the grant’s). A location, note or member id from another organization answers 404, exactly like an unknown id. A malformed id is 400. Error bodies are the kit’s `{ error, message, retryAfterSeconds? }`, and a failed validation is 400 `invalid_request` with no field details.

A town changed by hand on `PATCH` (without a `placeId`) takes the place off, since the place no longer describes the location; a rename, or a save of the same town, keeps it. Each write with a place id makes one billed Place Details call, after the policy, the location lookup and the location limit, so a refused or foreign request never reaches Google. That call is spent first from the account's `townwise:places` budget, the one the Places routes share: a used-up budget is 429 `rate_limited`, and a store outage is 503 `places_unavailable` (the routes carry no limiter of their own, so a write without a place id spends nothing and works during an outage, as before). The audit events say only whether the location has a place (`hasPlace`), never the id or the address.

`ForecastWindow` (U13B) is `{ available, reason: 'no_published_forecast' | 'not_covered' | null, runs, days, weeks, notCovered, accuracy }`, published runs only. A run is `{ id, metric: 'guests', model: { family, version, label }, engine, trainingSource, trainedFrom, dataThrough, madeAt, frozen, interval: { level: 0.8, widened }, backtest, live }`, `live` scored over the days that run supplied, never another run's. A day is `{ date, weekday, status: 'open' | 'closed' | 'booked', low, mid, high, baseline, reasons: { kind, label, effectPct, effect, sources, note, rule }[], model, noteGuests, moreNotes, moreRules, runId, madeAt, madeAfterDay, actual, inRange, scored }`, its numbers raw as stored (clients round). Since spec D42: `engine` is `'baseline'` for model family `seasonal_baseline` (the lab’s baseline engine, which a run file may now name) and `'model'` for every other family, derived and never stored, and a baseline run’s `label` is “Townwise's baseline from your recent weeks and the town calendar” where a model run’s is “Townwise demand model v{n}”; a day’s `scored` is true when live accuracy counted it; and `accuracy` is live accuracy over the window’s own days, each from the run the reader chose for it, with booked, closed and likely-closed days left out, `{ days, inRange, typicalErrorPct, from, to }` or null under 5 scored days, so a read of last week says how the forecast did whichever runs its days came from (each run’s `live` is unchanged). From the town's today on, a run reason's `effect` is `{ direction: 'more' | 'fewer' | 'same', pct, basis: 'model' | 'history', days, averageGuests }`: the model's where the run recorded `effectPct`, else how the location's own last 52 weeks usually ran (closed and likely-closed days left out, minimums per kind, `pct` rounded to the nearest 5 and `same` at 5 or less; `src/forecasts/effects.ts`, spec 14.4); null below a minimum, on a note's or a rule's reason and before today. `averageGuests` is, on a weekday's history effect, the average open day's guests it is held against (the mean over the history's open days, rounded to the nearest guest), which the client shows after "your average day"; null on the model's effects and on every other kind. The read computes it from the stored days, notes and rules it reads anyway (the stored days from the history's start), stores nothing and logs nothing. From the town's today on, `status`, `low`, `mid` and `high` include the location's notes (spec 14.5); `model` is the run's own `{ status, low, mid, high }`, `noteGuests` the guests notes add on an open day or a buyout's party on a booked day (0 when none), `moreNotes` the note reasons past the first 6 and `moreRules` the rule reasons past the first 6 (both still counted). A reason's `kind` is a run reason kind or `note`; `note` is `{ id, guests, outcome }` on a note's reason (`outcome`: `added`, `booked`, `closed`, `already_in_forecast`, `no_guest_count`, `not_counted`, `day_closed`, `day_booked` or `past_day`) and null on the run's, whose `effectPct` and `sources` a note's reason leaves null and empty. A business rule with a schedule (D31) applies as a note with those fields: its reason has `kind: 'rule'` and `rule: { id, guests, outcome }` (every other reason has `rule: null`), worded from the schedule, never the rule's text, and its guests count in `noteGuests`; a note that decides the day beats its closure or buyout (`outcome: 'overridden'`). `baseline` is null when a note changed the day's status; `inRange` stays the model's. A week is `{ from, to, openDays, low, mid, high, runId, madeAt, actual, inRange, noteGuests }`: the run's week row shifted by each day's adjusted `mid` less the model's (never below 0), its `openDays` by the days opened less the days closed, and left out only when a changed day has no model `mid`. `live` is `{ days, inRange, typicalErrorPct, from, to }` or null under 5 scored days; it leaves out closed and likely-closed days (spec D32). `estimates/about`'s `forecast` is `{ run, live }` for the newest published run and its own live accuracy, or both null.

A search is 10 to 15 autocompletes (debounced at 250 ms, nothing under 2 characters) and one details call, so `townwise:places` allows about 20 searches an hour, and two or three in a few minutes stay well inside it and inside `townwise:writes`, which counts them too. Each checked place is one details call, and each settled change to the checked places one map call (D29), so checking 25 places over five or six searches is about 140 calls. The map route lets any signed-in account sign maps of arbitrary place ids, up to 25 pins each; `townwise:places` and `townwise:writes` bound how many it signs, a signed URL never expires (as details' map already does not), and the Maps Static API's daily quota (`../infra/README.md`, step 17) is the hard cap on what loading them costs. A refused request is 429 `rate_limited` with `retryAfterSeconds`, except a calibration, which is 429 `calibrations_rate_limited` without it. Account keys are `acct:<userId>`, which the rate-limit module hashes before storing. [CONFIRM: limits]

It holds local values and placeholders only: the two key rings, the Google client ids, the staff list, the Anthropic key, the Places key, the Maps static key and its signing secret are empty, and `TOWNWISE_CALENDAR_KEY`, `TOWNWISE_GOOGLE_CALENDAR_CLIENT_ID` and `TOWNWISE_GOOGLE_CALENDAR_CLIENT_SECRET` are commented out, which leaves calendar links and Google calendars off. Key rotation for the two key rings is in `kit/auth/MODULE.md`.

## Kit modules

The code under `kit/` is ours to own. Record any change under `## Local changes` in that module's `MODULE.md` with the test that pins it. To take a kit fix: in a camkeith/modules clone, `git diff <commit in KIT.md> <new commit> -- backend/<name>`, apply it here, run `npm run verify`, and update the line in `KIT.md`.
