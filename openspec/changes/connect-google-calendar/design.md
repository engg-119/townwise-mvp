## Goals / Non-Goals

**Goals:**
- An owner connects a Google calendar on the web by signing in with Google, picks calendars, and their events show on the Calendar, in TownwiseAI and on every visit, kept current without the owner doing anything.
- Townwise holds the least it can: the narrowest read-only scopes, only an event's id, status, title, start and end, a sealed refresh token and sealed calendar ids, and nothing once the access is no longer needed.
- No Google token, code, calendar id, email address, calendar name or event title in a URL path or query, a log line, an audit event or an answer to anyone but the person whose Google account it is.
- Off by default in production, behind a Terraform flag, so a release carrying this code changes nothing until the owner turns it on.

**Non-Goals:**
- Writing to Google Calendar, or any scope beyond read-only.
- Connecting on native (decision 15); a separate "Disconnect Google" control (decision 11).
- Google Workspace domain-wide delegation, or service accounts.
- Push notifications (`events.watch`) or incremental sync (`syncToken`).
- Expanding repeating events in files and links: they stay counted, not imported.
- Any change to sign-in, to `api/kit/*`, or to the CSP (expected; decision 15 checks it).
- Any change to TownwiseAI's prompt, or to a tool's name, description or input (decision 16; only what `get_owner_calendar`'s saved result keeps changes).

## Decisions

### 1. Connect a Google calendar by signing in with Google (owner)

Owner, 2026-11-15: "i should be able to connect a google calendar". Decided: sign in with Google, read-only OAuth access, the owner picks which calendars to keep, Google's access stored sealed like calendar links are today, and the "unverified app" warning and 100-user cap accepted until Google approves the app. Everything below that the owner did not decide is marked Claude's call.

A Google calendar is a third kind, `google`, of the location's up to 5 calendars (D33): it takes a slot, its events are replaced by generation, it has a status, an "Updated" time, "Refresh now" and "Remove", and it is audited as `owner_calendar.*` with kind `google`, exactly as a link is. What is new is how it is connected and read. This reverses `connect-owner-calendar`'s non-goal "Google Calendar sign-in (OAuth)" and, for Google calendars only, "Expanding repeating events", since Google expands them itself (decision 7).

### 2. Scopes: the narrowest read-only pair (Claude's call)

Townwise asks for exactly `openid`, `https://www.googleapis.com/auth/calendar.calendarlist.readonly` and `https://www.googleapis.com/auth/calendar.events.readonly`. The calendar list scope lets the picker show the person's calendars and lets an add check one; the events scope reads events; `openid` (non-sensitive) returns an ID token whose `sub` the account check needs (decision 4). No `email` or `profile` scope: the ID token's `sub` is all Townwise reads from it. `include_granted_scopes` is false, so the token Townwise keeps grants only these three, not sign-in's `email` and `profile`.
*Alternatives:* `calendar.readonly` (one scope that also covers settings, ACLs and free/busy: broader than needed); `calendar.events.owned.readonly` (rejected: it hides calendars shared with the owner, which is how a separate bookings account's calendar usually reaches them).
Consent is granular: the connect handler reads the token response's `scope` and answers 400 `google_scope_missing` unless both calendar scopes were granted, storing nothing. It does not revoke then (revoking is project-wide and would also end the person's sign-in grant, decision 11); Townwise kept nothing, and the next try asks Google again.

### 3. The web flow: GIS code model in a popup, a confidential server, CSRF and state (Claude's call)

*The browser.* `GoogleConnect.web.tsx` loads GIS through one shared loader (`client/src/auth/gis.web.ts`, moved out of `GoogleButton.web.tsx` so both share one script tag) only when the person opens "Add a Google calendar", so Google sees nothing of the Calendar until they choose this. Once loaded it calls `google.accounts.oauth2.initCodeClient({ client_id, scope, ux_mode: 'popup', include_granted_scopes: false, login_hint, state, callback, error_callback })` and calls `requestCode()` inside the press of "Continue to Google", so the popup comes from a user gesture. `client_id` comes from the list answer (`google.clientId`, decision 8), so the browser asks Google for a code for exactly the client the server exchanges it with; the alternative, the bundle's `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, could drift from the server's value. `login_hint` is the person's own email address (from `GET /api/me`), which goes only to Google's window, never to a Townwise URL. `state` is 128 random bits from `crypto.getRandomValues`, new for each press: the callback drops any answer whose `state` differs, and a "Stop waiting" press forgets it, so a late code from an abandoned window is never posted.

*The exchange.* The callback posts `{ code, agreed: true }` in a JSON body to `org.google_calendars.connect`. The API, a confidential client, exchanges it at `https://oauth2.googleapis.com/token` (`grant_type=authorization_code`, `client_id`, `client_secret`, `code`, `redirect_uri=postmessage`, confirmed by the runbook check). GIS's code model offers no PKCE, so the client secret is what binds the code to Townwise: a code stolen from the browser is useless without it.

*CSRF and login CSRF.* The connect route is a cookie-session write, so the kit's transport already refuses it without an allowlisted `Origin` (`api/kit/auth/src/transport.ts`), which is the protection Google's `X-Requested-With` check stands in for. The account check (decision 4) blocks the other attack, an attacker getting a victim to connect the attacker's Google account: the code's ID token must name the victim's own sign-in account.

*The ID token.* It arrives directly from Google's token endpoint over TLS, so the handler checks its claims without a signature check (OpenID Connect Core 1.0, 3.1.3.7, item 6): `iss` is `https://accounts.google.com` or `accounts.google.com`, `aud` is the client id, `exp` is in the future (5 seconds of tolerance), and `sub` is a non-empty string. The kit's `verifyGoogleIdToken` is not reused: it needs an `email` claim, which this flow does not ask for, and `api/kit/*` stays unchanged.
*Alternative:* the redirect mode with a server callback route (rejected: a new public route, the code in a URL that server-core would log, and a full-page navigation away from the popover).

### 4. One connection per person per organization, for the account they sign in with (Claude's call; open question 1, decided by the owner on 2026-11-16)

A connection (`tw_google_connections`) is one per (organization, person), unique on (`orgId`, `userId`), shared by every Google calendar that person adds to any of the organization's locations. At connect the ID token's `sub` must equal the kit user's `googleSubject` (`ctx.authStores.users.findById`), or the answer is 409 `google_other_account` and nothing is stored. The kit's unique `googleSubject` then means one Google account backs at most one person, so Google's project-wide revoke (decision 11) can only ever end that person's own access. A calendar of another Google account (a separate bookings account) is shared with the sign-in account in Google Calendar first; the picker says so.
*Alternative:* any Google account, keeping its subject on the connection and checking every organization before each revoke (rejected for now: more stored identity and a revoke that could end another Townwise person's connection or sign-in grant for the same account). Open question 1 asked the owner.
*Decided (owner, 2026-11-16):* the owner confirmed this default: a person connects only the Google account they signed in with. It is no longer a [CONFIRM] in D39 or the CONFIRM index.

### 5. Google's access is sealed, and nothing else is kept (Claude's call)

- The refresh token is sealed with `calendar/secret.ts` under `TOWNWISE_CALENDAR_KEY`, unchanged, and stored as `sealedRefreshToken`. It is opened only on the server, to refresh access or revoke it, and never answered, logged or audited.
- No access token is stored: each use refreshes one (about an hour of life), uses it for that read and drops it. The few extra token calls (4 refreshes a day per calendar) cost nothing under the quotas.
- A Google calendar's id is sealed the same way in the source's existing `sealedAddress`, because a shared or primary calendar's id is an email address. The stored id is Google's real id from the calendar list (the primary's too, not the `primary` alias), so two people adding the same shared calendar can be told apart from two people adding their own primaries (decision 8's duplicate check).
- If Google ever answers a new refresh token on a refresh, it replaces the stored one (through `calendar/google-access.ts`, decision 11, the one place a stored token is opened or replaced).
- *Alternative:* a separate key for Google tokens (rejected: more Key Vault and Terraform plumbing for the same consequence of a lost key, reconnecting). Changing the key now also breaks every Google connection (`key_mismatch`); the runbook's "Never change the key" says so.

### 6. Data model (Claude's call)

- New tenant store `tw_google_connections` (`api/src/stores/google-connections.ts`, `OrgScope` methods): `orgId`, `userId`, `sealedRefreshToken`, `scopes` (as granted), `agreedAt` (decision 12), `connectedAt`, `updatedAt`, `revokedAt` (null until Google answers `invalid_grant`), `checkAt` and `leaseUntil` (decision 10). `checkAt` is never null: `markForCheck` sets it to now, and `clearCheck` sets it 24 hours ahead, so every connection is checked at least daily. Unique (`orgId`, `userId`); an index on `checkAt`. No email, name or Google subject is stored. Methods: `upsert`, `findForUser`, `find`, `sealedToken`, `replaceToken`, `markRevoked`, `markForCheck`, `clearCheck`, `remove`, `listForOrg`, `removeForOrg`.
- `tw_calendar_sources` gains kind `google` and `googleConnectionId` (an ObjectId, null for files and links). For a Google calendar `sealedAddress` holds the sealed Google calendar id, `host` is null, `skippedRepeating` is 0 and `nextRefreshAt` is set as for a link. The slot limit, generations, `eventCount`, `lastSuccessAt`, `consecutiveFailures` and `lastManualRefreshAt` apply unchanged. The store gains `countForConnection(scope, connectionId)` and `removeForConnection(scope, connectionId)` (events, then sources, then events again, as `removeWhere` does). `claimManualRefresh` matches `kind: { $in: ['link', 'google'] }`. `sealedAddress` stays link-only; a Google calendar's sealed id and connection are read with `googleSource(scope, locationId, calendarId)` (one calendar, for a refresh) and `googleSources(scope, locationId)` (the location's, for the duplicate check and the picker's `added`).
- New statuses: `google_revoked`, `google_not_found`, `google_forbidden`, `google_rate_limited`, `google_unavailable`; `key_mismatch` is reused for a token or id the key no longer opens.
- *As built (task 1.5, 2026-11-15):* `upsert` takes `sealedRefreshToken: null` to keep the stored token (decision 8's rule when Google sends none) and then updates only a row that is there, answering null when there is none; `clearCheck` also lets go of a check's lease. *Correction (group 1 review, 2026-11-15):* the null-token update also matches only a row whose `revokedAt` is null (compare-and-set), so a refusal `markRevoked` records between connect's `storedTokenOpens` and the upsert is never cleared over a dead token; it then answers null, which connect treats as the no-connection branch (revoke the new access token, 409 `google_connect_again`). *Correction:* registering the store in `stores/index.ts` changes what `api/test/indexes.test.ts` lists (the `tw_` collections, and the models whose compound indexes lead with `orgId`), a file no group owned, so task 1.5 added `tw_google_connections` and `TwGoogleConnection` there. *Correction (group 3 review, 2026-11-16):* the store also gains `releaseCheck`, the refresh loop's compare-and-set end of a connection check (decision 10).

### 7. Reading a Google calendar (Claude's call)

*The port.* `api/src/calendar/google.ts`, shaped like `places/google.ts`: global `fetch` (a fake fetch in tests), the hosts constants (`https://oauth2.googleapis.com` for token and revoke, `https://www.googleapis.com/calendar/v3` for the calendar list and events), `redirect: 'error'`, `AbortSignal.timeout(10_000)` per call (combined through `AbortSignal.any` with a caller's optional `signal`, so the refresh loop's close aborts a call in flight, decision 10), each body read with a 2 MB cap, and failures as a code plus Google's HTTP status, never Google's message or body. Methods: `exchangeCode`, `refreshAccess`, `listCalendars`, `getCalendar` and `listEvents`. Revoking is a separate export, `revokeGoogleGrant(token, { fetch?, signal? })`, since Google's revoke needs no client id or secret: ending access then works whenever `TOWNWISE_CALENDAR_KEY` opens the token, with the Google client off too (decision 11). It POSTs `token` in an `application/x-www-form-urlencoded` body to `https://oauth2.googleapis.com/revoke` with no query string, so a token never sits in a URL, an error object or a fake fetch's recorded URL. Calendar ids go into paths through `encodeURIComponent`. The guarded fetcher (`calendar/fetch.ts`) is not used: the hosts are fixed, so there is no owner-supplied host and no request-forgery surface, and `isolation.test.ts`' rule that only `calendar/fetch.ts` opens a socket holds.

*The read* (`api/src/calendar/google-events.ts`): refresh access once, then `events.list` on the calendar with `singleEvents=true`, `orderBy=startTime`, `showDeleted=false`, `eventTypes=default` (no birthdays, out-of-office, focus time, working location or Gmail events), `timeZone` the town's zone, `maxResults=500` and `fields=nextPageToken,items(id,status,summary,start,end)`, so a description, location, attendee or organizer never reaches Townwise. Since `timeMin` bounds an event's end, `timeMax` its start, and `startTime` order is ascending only, one read of the whole window would fill the 2,000 from 401 days back, and a calendar averaging 5 or more events a day (a bookings calendar, or a few daily standing events, which Google expands) would keep nothing ahead. So the read goes ahead first (Claude's call): (1) the events ahead, `timeMin` the town's today less 1 day and `timeMax` today plus 401 days, at 00:00Z; (2) with whatever is left of 2,000 events and 8 pages in all, the events before, newest slice first: today less 30 days to today, then less 90 to less 30, less 210 to less 90 and less 401 to less 210, at 00:00Z (the outer bounds a day of margin on each side of the 400-day window filter). Each follows `nextPageToken` (Google may answer fewer than 500 a page): the read ahead stops at 2,000 events, and a slice before is read to its end, or left out when the page budget cuts it short (what it read would be that slice's oldest events, a gap away from the newer slices); an item read twice counts once, by its id. The loop's close is checked between pages (decision 10).

*Mapping* reuses `ics.ts`'s rules through helpers it now exports (`townClock`, `spanOf`, `titleOf` and a shared `keepWindow(events, today, options?)`; `parseIcs`'s behavior unchanged): the uid is the item's id (unique per instance); the title is `titleOf(summary)` (cut at 200 characters, ics.ts's word for none); an all-day `date` has an exclusive end; a timed `dateTime` instant is converted to the town's wall time, with ics.ts's hours rule (hours only when it starts and ends on one date or ends by 06:00 the next morning); `cancelled` items are skipped; events within 400 days of the town's today are kept. The cut differs from files and links for Google only: the events that end on or after the town's today come first, the first 2,000 by start, and the earlier ones read fill what is left, the latest first (`keepWindow(events, today, { aheadFirst: true })`). Files and links keep the first 2,000 by start, as today (Risks). [CONFIRM: a Google calendar keeps its next 2,000 events first, then earlier ones]
*Correction (task 1.1, 2026-11-15):* ics.ts's `titleOf` also undid iCalendar's escapes (`\,`, `\;`, `\\`, `\n`), which a Google summary does not use, so a backslash in a Google title would have been lost. The unescaping moved into `parseIcs`'s own call, so `titleOf` takes plain text and a file's titles are unchanged.
*Correction (group 1 review, 2026-11-15):* task 1.3 read the window before as one range from today less 401 days, which Google lists oldest first only, so when the room left after the events ahead was smaller than the past, only its oldest pages were read and the latest-first cut kept the latest of the oldest: with 4 events a day ahead and 3 a day before, the 7 months just before today were empty while a year ago showed, against the Risks line ("loses its oldest"). The window before is now read in the four slices above, newest first, so the cut keeps the days just before today. A sparse calendar costs 5 events calls a refresh instead of 2, within the 8 pages.

*Repeating events are kept* (reversing a non-goal for Google only): Google expands them itself, exceptions and time zones included, so Townwise needs no recurrence engine, which is why the `.ics` path skips them; standing weekly events are what an owner's Google calendar holds. Their instances count against the 2,000 (Risks).

*Sync:* the whole window on every refresh, replaced by generation. No `syncToken`: it cannot be combined with the window, its deltas do not fit the generation replace, the window moves daily, and the volume is small.

*Errors, by Google's answer:* token `invalid_grant` is `google_revoked`, and the connection's `revokedAt` is set so its other calendars fail fast without calling Google (decision 10); token `invalid_client` is `google_unavailable` (a configuration fault); events 401 is `google_revoked`; a 403 whose reason is `rateLimitExceeded`, `userRateLimitExceeded` or `quotaExceeded`, or a 429, is `google_rate_limited`; a 403 whose reason is `accessNotConfigured` or whose detail is `SERVICE_DISABLED` (the Calendar API not enabled in the project) is `google_unavailable`, with its own client code `api_disabled`, so a project-wide setup fault is not mistaken for refusals on single calendars; any other 403 is `google_forbidden`; 404 or 410 is `google_not_found`; a 5xx, a network failure, a timeout, an aborted call or an over-cap body is `google_unavailable`. The client matches on `reason` (the legacy `error.errors[].reason`, or `error.details[].reason`), never on the domain alone, since Google's general errors such as `accessNotConfigured` are not on the Calendar page and their domain is not documented there; it reads the reason only to pick a code, and keeps nothing else of the body. The client's codes are a fixed enum: `invalid_grant`, `invalid_client`, `unauthorized`, `rate_limited`, `forbidden`, `api_disabled`, `not_found`, `unavailable`, `bad_response`. Backoff is phase 1's (6 hours, then 24).

*Logging a failure:* `calendar/google.ts` never logs. Every caller of the client (the refresh loop, Refresh now, the add, connect and the picker's list) reports a failure through one helper, `logGoogleFailure(logger, op, error)` in `calendar/google-access.ts`, which logs exactly `townwise.google_calendar_failed { op, status, code }`: `op` one of `token`, `calendar_list`, `calendar`, `events`, `revoke`; `status` Google's HTTP status or null; `code` from `GoogleCalendarError`'s enum, never Google's `error`, `error_description`, message or body, and never a URL.

### 11. Ending access and revoking the grant (Claude's call; open question 3, decided by the owner on 2026-11-16)

`api/src/calendar/google-access.ts` holds every use of a stored Google token: opening it, replacing it, revoking it, and the reads that need it (`readGoogleSource` for the loop and Refresh now; the add's, connect's and the list's access through one `googleAccessToken` helper; `storedTokenOpens` for connect's rule), with `logGoogleFailure` (decision 7). It takes a narrow `GoogleAccessDeps` (`connection`, `stores`, `key`, `logger`, `now`, the Google client or null, `revokeGoogleGrant`, an optional abort signal), which handlers build from their `TownwiseContext` and the refresh loop from its own deps. `endGoogleAccess(deps, scope, connectionId, reason)` runs in an order that a retry or the check (decision 10) completes:
1. Mark the connection for a check (`checkAt` now).
2. Remove every Google calendar of the organization that the connection backs (events, then sources, then events), so a departed person's events leave the location first.
3. Revoke at Google with the opened refresh token through `revokeGoogleGrant` (best effort, 10 seconds; 200 or 400 `invalid_token` both count as done; a failure logs `townwise.google_revoke_failed { status }`), unless the same person has a connection row in another organization (a cross-tenant lookup by person, `hasGoogleConnectionElsewhere` in `stores/cross-tenant.ts`): Google's revoke is project-wide, so revoking a leftover row would end the person's live connection there. `revokeGoogleGrant` needs no client id or secret, so it runs whenever `TOWNWISE_CALENDAR_KEY` is set, with Google calendars switched off too (a rollback, or the abandonment path). A token the key no longer opens cannot be revoked; the person can remove Townwise at myaccount.google.com/connections, which the privacy page says.
4. Delete the connection row, whether the revoke worked or not, so Townwise holds nothing.
5. Log `townwise.google_access_ended { connectionId, calendars, reason }`.

When it runs:
- Seat loss: the three callers of `removeActiveSeat` (`team.removeMember`, `org.leaveOrg`, `admin.removeOrgMember`) first mark the person's connection in the organization for a check (`markPersonForCheck(deps, scope, userId)`, before `removeActiveSeat`), then, on a `removed` result and after the seat's own audit event, end it (reason `seat_removed` or `left`). Marking first matters because once the seat is gone a retry of the remove or the leave answers 404, so a request that stopped between the seat's removal and `endGoogleAccess` could never be finished by the caller; the check, due at once, finds no seat and ends the access. ## Risks / Trade-offs

- [Google's revoke is project-wide: ending calendar access also ends the person's sign-in grant, so their next "Continue with Google" shows Google's consent screen once] → The words never promise otherwise; the same-account rule and the other-organization check (decisions 4 and 11) keep a revoke from touching anyone else.
- [The unverified-app warning and the 100-user cap until Google verifies; verification can take about 10 days and needs a demo video and domain verification] → Accepted by the owner (decision 18); off by default until the runbook step; the explainer warns.
- [A consent screen left in "Testing" gives 7-day refresh tokens and admits only test users, and the status is the whole project's, sign-in's client included] → The runbook's step requires "In production" before the flag is turned on and never changes the production project's status; local testing on a Testing screen uses a separate development project (Migration Plan step 2). If it is missed, refreshes turn `google_revoked` a week after each connect, and those rows say how to reconnect.
- [The GIS code model has no `prompt` option (only `select_account`), so a reconnect for an account that already granted may return no refresh token, and a dead token can sit under a live grant] → The stored token is kept only when it is not revoked and opens under the current key; otherwise the API revokes and answers 409 `google_connect_again` (one more press, which consents fresh); the runbook confirms a refresh token on a first exchange.
- [The popup exchange's `redirect_uri` (`postmessage` against "the calling page's origin")] → A wrong value fails every exchange with `redirect_uri_mismatch`, which is visible at once; the runbook check settles it before the flag is turned on in production, and the value is one constant.
- [Expanded repeating events count against the 2,000: a daily event across the 801-day window takes 801 of them, and a calendar of 5 or more events a day fills the 2,000 within the year ahead] → Google calendars read and keep the events ahead first (decision 7), so a busy calendar keeps its next 2,000 events and loses its oldest; owners pick which calendars to add, and the row's count shows a full calendar.
- [Files and links still keep the first 2,000 by start, so a busy `.ics` link (a bookings feed) can keep only past events] → Unchanged by this change; applying decision 7's ahead-first cut to them is a follow-up.
- [Staff under view-as, or with the organization open as its admin, could read Google event titles, against Google's "affirmative agreement to view specific" data] → Under view-as and open as admin alike, Google calendars show as "Google calendar" and their events as "Google calendar event", TownwiseAI's reads in staff's turns included (decision 12 and its group 6 review correction); what remains is a TownwiseAI reply that quotes a title, disclosed at connect and agreed to there. The owner confirmed this default on 2026-11-16 (open question 2).
- [Limited Use: Google event titles reach Anthropic when TownwiseAI reads them] → A user-facing feature, disclosed in the explainer and on the privacy page; Anthropic does not train on it; the saved conversation keeps a stub, so titles are sent only in the turn that read them (decision 16).
- [The calendar read's stub (decision 16) also applies to files and links, so a later turn that needs the events calls the tool again] → One more tool call in that turn, at a tool result's cost; the thinking blocks after the stub in the reading turn are not saved, as for `read_data_item`.
- [Seat loss removes Google calendars others at the location rely on (a manager's bookings calendar goes when they leave)] → The explainer and privacy page say so; another member it is shared with can connect it again. The owner confirmed on 2026-11-16 that they leave (open question 3), rather than staying frozen.
- [Removing someone else's last Google calendar ends their Google connection] → An unused grant is a credential Townwise should not hold; they reconnect in one press if needed.
- [Changing `TOWNWISE_CALENDAR_KEY` also breaks every Google connection] → `key_mismatch`; people reconnect; the runbook's "Never change the key" says so.
- [A revoke fails (Google down) and Townwise deletes the row anyway] → Townwise holds nothing; the grant at Google lapses after 6 months unused, and the person can remove it at Google; the failure is logged. With Google calendars switched off, the revoke still runs (`revokeGoogleGrant` needs only the token and the key, decision 7).
- [A request stops between a seat's removal and ending that person's access, and its retry answers 404] → The connection is marked before the seat is removed, so the check ends it at the next look; every Google read first checks the person's seat, and every connection is checked daily (decisions 10 and 11).
- [Two adds of the same shared calendar at once both pass the duplicate check] → Rare; its events show twice until one is removed (keys are `{calendarId}:{uid}`, so nothing collides).
- [Concurrency: a removal ends a connection while its person is mid-picker] → The add re-checks its connection after storing and answers 409 `google_not_connected`, or, storing while the end is revoking, answers 201 and loses the calendar to the end's second sweep; the person connects again.
- [Stacking: refine rewrites `YourCalendars.tsx` into a Popover and MODIFIES the same requirement] → This change's client group runs only after refine's group 1 has landed, and its MODIFIED block is refine's block plus the Google lines.
- [Old clients: today's `z.enum(['file', 'link'])` fails the whole list once a `google` row exists] → This change loosens the parse; web ships the API and client together, and a native build older than this change shows "Couldn’t load your calendars" for a location with a Google calendar until it updates (Google calendars are off until enabled, which bounds it).
- [GIS may change, or need a new origin] → The browser check; any new origin updates MODULE.md, the static web app config and the tftest together.
- [Google's quotas may start to charge for overages] → Expected volume (at most 5 calendars a location, 4 refreshes a day, a few requests each) is far below the free limits.
- [Loading GIS on the Calendar lets Google see that visit] → Only after the owner opens "Add a Google calendar"; the privacy page says so, as it does for the sign-in page.
