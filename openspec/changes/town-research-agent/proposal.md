## Why

On 2026-11-19 the owner asked: "do i have a research agent (that supports multiple research threads that builds up a graph / calendar of events that are important and anything that could affect a small business within a town) yet set up yet?" It is not set up. Milestone 1 of `docs/milestones.md` ("Develop the locality research agent to identify Hanover-specific demand drivers") was never built. Today's town calendar is hand-curated code (`api/src/town-calendar-data.ts`, Hanover only, 38 rows from `modeling/dartmouth_calendar_2025_2026.csv`), and TownwiseAI searches the web only inside a chat turn a person started (D37, at most 3 searches a request).

The owner then decided: "1. per town and per restaurant right? maybe map out competition as well and see if they have any public competing events etc 2. staright into the calendar and a user can always edit them manually or ask townwise ai to correct them in some way. build both end to end".

By the owner's rule of 2026-11-16 the feature ships on by default. Spec decision **D66** (D64 is PR #126's, D65 is `forecast-training-status`'s; check develop's spec and the open branches again before writing it).

## What Changes

- **A research runner in the API.** A leased loop in each API replica (`api/src/research/runner.ts`), shaped like the file reader (`files/ai-reader.ts`), plans and runs research in the background. It needs no infra change: the API already has the Anthropic key, Places, Valkey and the static map signer.
- **Per town and per restaurant.** Each of the twelve towns with a location gets a **town run** each week: six parallel threads (schools, sports, arts and festivals, civic, tourism and seasons, markets and community), shared by every restaurant in the town. Each location gets a **location run** when it is created, when its place is picked or changed, then each week: its neighborhood (its own public events, nearby venues, street closures) and its competitors. A location in a town outside the twelve gets one combined thread of its own. An org admin can press **Research now** (rate limited).
- **Two calls a thread, sources checked by code.** A thread first gathers with Anthropic web search (and web fetch, behind a switch), then a second call with no tools extracts events as JSON that cite sources by id from a ledger built in code from what the searches returned. The model never types a URL. An event survives only with a known source, parsable dates in the window, and a title with no URL, email or phone number. Confidence comes from code (a date quote found in the cited text, and how many sites agree), never from the model alone.
- **A small graph.** Venues, organizations, teams and schools found on the web are stored as entities, linked to events (at, hosted by). Competitors are Google place ids linked to the location (competes with). The Calendar says where and who; the Town tab lists who and where.
- **Competition.** A new Places Nearby Search finds the location's nearest restaurants, bars and cafes. Their names go into the competitors thread's prompt only, never into storage. A Competition card on the Town tab shows a lettered map and each competitor's upcoming public events (trivia, live music, specials, festivals).
- **Straight into the Calendar.** Findings show on the Calendar with no accept step, under a new "Found by research" filter, with sources, an "Unconfirmed" chip for low confidence and a "Cancelled" chip. They stay outside `townEvents()`, so the lab input, its golden files, term state and forecast effects do not change; they reach the forecast only as notes TownwiseAI suggests (weekly suggestions read them) or saves (D59).
- **Edit, hide, or ask TownwiseAI.** Any member can edit, hide or restore a researched event on the Calendar. Each change is an append-only revision for that location only: it never changes another location's or another organization's calendar. A new chat tool, `correct_calendar_event`, makes the same change when a person asks, through `agent/apply.ts` as `event.correct`, with Undo in TownwiseAI's activity.
- **Owners see it run.** Following D65's running-and-done pattern: the Town tab and Calendar say when research is running and what it found, TownwiseAI's activity gains `research_done`, and the dashboard says "Researching".
- **Bounds.** Location threads spend the organization's TownwiseAI month (automatic runs leave $5 of it). Town threads spend a new system month capped by `TOWNWISE_RESEARCH_TOWN_MONTHLY_USD` (default $40). Each thread reserves its ceiling, including searches and their pages, and settles to what it cost. `TOWNWISE_RESEARCH` (default true) is the kill switch (false in `api/production.env` until the live eval passes and the privacy page ships), and an organization switch lets an org admin turn it off.
- **Privacy.** Research sends public facts only: the town, public calendar titles, and, once the owner answers whether Google's terms allow it (`TOWNWISE_RESEARCH_PLACES_TO_AI`, false in production until then), the restaurant's Google name and address and competitors' Google names, types and websites. It never sends the location's name as typed in Townwise, the organization's name, sales, notes, rules, owner calendar titles, emails or people's names. Logs carry ids, codes and counts only. The privacy page, `docs/portal/tuning-chat.md` and `docs/portal/estimates.md` say what it sends in the same release.
- **Evals.** Deterministic CI tests with recorded fixtures, and an opt-in live eval (`api/scripts/research-eval.ts`, never in CI) that runs Hanover's town threads with the curated rows held out and scores recall, source validity, dates and duplicates. It runs once before shipping, and its report is committed.

## Capabilities

### New Capabilities
- `town-research-runs`: planning, running, leasing, retrying and paying for research runs and their threads, per town and per location, with the switches and Research now.
- `research-findings`: the gather and extract calls, the source ledger, the checks, confidence, the merge into stored events and entities, and what is sent and logged.
- `researched-calendar`: how researched events reach the Calendar, Home, the Town tab, chat reads and weekly suggestions, and the per-location edits, hides and restores.
- `research-chat-corrections`: the `correct_calendar_event` chat tool, its gate, and its Undo through the agent changes ledger.
- `competition-map`: Places Nearby Search, the competitors thread's inputs, and the Competition card and route.
- `research-evals`: the CI fixtures and the opt-in live eval with its ship gate.

### Modified Capabilities
(none: no capability under `openspec/specs/` changes; the earlier changes this one touches are not archived)
