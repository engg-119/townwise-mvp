## Context

What exists (develop at cb8e3f53), read for this design:

- **Calibrations** (spec 6.23, `api/src/stores/calibrations.ts`, `tw_calibrations`). One record per lab run: `requestedBy { userId, role, via }` with role `org_admin | superadmin | system` and via `chat | console | file | scheduled`, status `queued | running | succeeded | failed` (`LIVE_STATUSES` the first two), `failure`, `gate { published, reason }`, `runId`, `championRunId` (null when the location had no current run at the start), `dataThrough` set at the input fetch, `scorecardJson`, `requestedAt`, `startedAt`, `finishedAt`, and `liveLocation` (a unique partial index: one live calibration per location, so a live calibration is always the location's newest). Nothing records what started a system calibration, how many days it used or its first day. The schema is `strict: 'throw'` with `minimize: false`.
- **Who starts one** (`api/src/lab/service.ts` `launch`). People: TownwiseAI chat (`via: 'chat'`), a pressed TownwiseAI file read and a bookings confirm (`via: 'file'`), staff in the console (`via: 'console'`). Staff can also start one through chat or a file read while they have the organization open as admin: `chat/tools/calibration.ts` and `files/ai-actions.ts` then record `role: 'superadmin'` with `via: 'chat'` or `'file'`. The system, as `SYSTEM_REQUESTER` (`role: 'system'`, `via: 'scheduled'`): the weekly refresh (`lab/schedule.ts` `consider`) and D59 refits (`considerRefit`). A weekly start is linkable through `tw_forecast_weeks.calibrationId`; a refit is not.
- **Refit marks** (D59, `tw_locations.refit { wantedAt, startedAt, starts }`; `starts` is declared `default: undefined`). `wantRefit` (`$max`) is called by `agent/refit.ts` `wantRefitFor` (sales uploads and staff setup uploads, a person's notes and rules, undo of a file read, agent undo, calendar answers) and directly by `files/worker.ts` (the file reader's days) and `agent/apply.ts` (TownwiseAI's changes). The mark stores no cause. The hourly pass takes a mark (`stores/cross-tenant.ts` `refitCandidates`) once it is 15 quiet minutes old and `refit.startedAt` is absent or at least 24 hours old (`REFIT_EVERY_MS`), and only when the pass's weekly part ended `ran` (not `deadline`, `paused` or `off`). `considerRefit` then clears the mark without a start when the history is under 230 days or the input's fingerprint equals the reference calibration's (`calibrations.reference`: the newest succeeded calibration with a gate, not `forecasts_off` or `champion_changed`); holds it past the live cap of 3 or the weekly cap (refits and week rows over 7 days); and otherwise starts, setting `startedAt` on a start or a refusal and clearing the mark by compare-and-set on `wantedAt`.
- **First forecast after onboarding.** It already starts on its own: the upload marks a refit, and the pass starts it, usually within about 15 to 75 minutes, when the lab runner is on, `TOWNWISE_WEEKLY_FORECASTS` is true, staff have not paused the schedule, the organization is active with forecasts on, the history spans 230 days (`GATE.baselineMinHistoryDays`) and the caps allow. The weekly cap or a Monday weekly part that runs out of time can hold it longer. Under 230 days the pass clears the mark and nothing runs. A first forecast is published only when the gate passes (G1 included). A location whose first run the gate held keeps a reference, so the pass starts another only once a new mark's data changes the fingerprint (a later upload) or the Monday weekly path finds new data.
- **A timed-out calibration.** A live calibration older than 20 minutes (`CALIBRATION_TIMEOUT_MS`) is failed `timeout` by `expireStale`, which writes, on the next start, staff read (GET /api/admin/orgs/:orgId/calibrations), chat tool or pass. The pass expires only system calibrations (`liveScheduledCalibrations`) and the location it considers. There is no sweep, so a dead run can read `queued` or `running` for hours. Spec 7.3 and `api/test/chain.int.test.ts` require every GET to write nothing, but the staff calibrations list is already a GET that expires stale records (`handlers/calibrations.ts` `listCalibrations`).
- **Calibration state** (14.1, `api/src/calibration.ts`). Derived on every read: `no_sales_data | not_calibrated | calibrated | stale` (`not_calibrated`: sales but no published run now), served by GET /api/org's location summaries, the sales GET and the upload answer. The client's `calibrationSchema` (`client/src/portal/schemas.ts`) is a strict `z.discriminatedUnion('state', ...)` inside the GET /api/org parse, so an unknown `state` breaks every page of an older client; an unknown key is stripped. Switches on `state`: `upload/copy.ts` `calibrationHeading` and `calibrationLine`, `ModelCard.tsx` `staleLine`. 14.3 reserves `queued`, `calibrating` and `failed`.
- **Activity** (`api/src/agent/activity.ts`). `ACTIVITY_SOURCES` is append-only and already reserves `forecast_made`. Items from every source are merged and cut to `MAX_ACTIVITY` (20); `agent_change` alone reads 20. The client parses each item through `known()`, so an unknown kind is dropped, and renders with an exhaustive `activityLine` switch. Items carry ids, dates and counts, never a figure; the panel (GET /api/org/locations/:locationId/agent, `member` policy) is read under view-as. The agent page opens its panel from `?panel=questions` (Home's questions link); the panel shows only on the new-chat landing and is a collapsed row at phone width.
- **Words.** `GATE_WORDS` (`lab/gate.ts`) and `FAILURE_WORDS` (`lab/service.ts`) are staff words ("stays a draft for Townwise staff to review").
- **Publishing.** The lab callback's `storeDraft` upserts the run on its file hash, records the result, gates it (`gateDraft`, which returns early, leaving `gate: null`, when the run is no longer a draft or another calibration made it), publishes by a draft-to-published compare-and-set (`publishDraft`; a staff withdrawal or deletion meanwhile wins) and then finishes the calibration `succeeded`. Staff can publish a held draft from the console (`handlers/forecast-runs.ts`), which sets `publishedBy`. A run keeps `publishedAt` after a withdrawal.
- **Email** (D14, `api/src/mail/`). Two kinds, `request_received` and `request_approved`, each to the person it concerns. `EmailRef.requestId` is required. The mailer's header says "Nothing about a send is stored", D14 and the privacy page say the same and that Townwise sends no other email, and "Email writes no audit event". `ctx.mailer` is on the API's `TownwiseContext`, which the /lab callback uses.
- **Client refresh.** No page polls the org. `reloadOrg()` drops the org to `loading`, so the dashboard flashes its skeleton; LocationShell keeps the previous org. `files/useImport.ts` (AppState-aware poll) and `data/item/AiSection.tsx` (saw running, now announce the end) are the templates.

## Goals / Non-Goals

**Goals:** an owner sees, on the pages they already use, when their forecast is being updated and when a first forecast is next or being built; can read the location's recent finished runs in TownwiseAI's activity, with what started it, the days it used and what happened, failures included, reached by a link from the dashboard, Home and the model card; sees on Home why a first forecast was not published, whenever they come back; and is told by email once when a location's first forecast is published. An older client keeps working. No GET writes. One pattern D66 reuses.

**Non-Goals:** a live training view or loss curve (staff keep D50's post-hoc RunTraining); a separate run-history page; starting the first forecast sooner than the hourly pass; emails for later runs or failures; stating a minimum history anywhere an owner reads (14.1's DECISION NEEDED stays open); showing owners a run's accuracy in the history (the model card already shows the published run's); changing `via`, the gate, the lab, its input schema or model version.

## Decisions

### 1. Additive fields, not a new state

Every calibration answer gains `updating: { stage: 'running' | 'waiting'; since: string } | null`, beside the existing fields of every union member (`null` on `no_sales_data`). The `not_calibrated` member also gains `lastRun` (decision 4). The four states and their headings do not change.

- An older client strips the unknown keys and parses every answer as today. A new `state` would fail GET /api/org's parse on an older client and blank every portal page, and would force a case into each switch on `state`.
- Updating is orthogonal to the state: a `calibrated` or `stale` location can be updating, and so can a `not_calibrated` one (its first forecast). A state would have to multiply (`stale_updating`) or lose the published facts the model card shows while it updates.
- 14.3's reserved names stay reserved: they describe a stored model's state, and updating is a run in flight.

The client's schema takes `updating` and `lastRun` as `.optional()` (an API from before reads as not updating, with no last run), the precedent of `placeId` and `offDayCount`, and with `.catch(null)`, so a stage or reason added later reads as none on this client instead of failing GET /api/org's parse. API tests that `toEqual` a calibration object (`sales.int`, `locations.int`, `staff-setup.int`) gain `updating: null` (and `lastRun: null` on `not_calibrated`). [CONFIRM: the forecast's progress is a field beside the calibration state; queued, calibrating and failed stay reserved]

Alternatives: a sibling key on the location summary (the sales GET and upload answer would need it too, and the words need the state's day counts anyway); a new `updating` state (breaks older clients).

### 2. The two stages, read only

`calibrationFor` reads the location's newest calibration (`calibrations.list(scope, 1, locationId)`, the `{ orgId, locationId, requestedAt }` index; the live one when one is live), before the published runs (the lab publishes a run before it finishes its calibration, so a finished calibration is never read without its published run), and its refit mark, and never writes:

- **`running`**: the newest calibration is live (queued or running) and its `requestedAt` is less than `CALIBRATION_TIMEOUT_MS` (20 minutes) ago; `since` its `requestedAt` (`startedAt` is null while queued). One past its 20 minutes reads as not updating, without `expireStale`, so the GET stays a read (7.3); it reads as a failed run in `lastRun` and the history (decisions 4 and 6). The next start, staff read or pass still fails it `timeout` as today. Every live calibration counts, staff's and chat's included: it is the location's forecast being updated, whoever asked. [CONFIRM: owners see every live calibration of their location as updating, including one staff or another admin started] [CONFIRM: a calibration past its 20 minutes reads as not updating, and as a failed run, with no write, until the next start or pass fails it]
- **`waiting`**: the hourly pass will take the location's refit mark on its own terms, and nothing of the location has succeeded yet. All of: the state is `not_calibrated`; the newest calibration is not `running` (above); `calibrations.reference(scope, locationId)` is null (no calibration of the location succeeded with a judged gate, so the pass cannot find the fingerprint unchanged); `refit.wantedAt` is set and `refit.startedAt` is absent or at least `REFIT_EVERY_MS` (24 hours) old, `refitCandidates`' own predicate, sharing its constant; `nextRefreshFor`'s conditions hold (lab runner, weekly forecasts, schedule not paused, organization active with forecasts on); and the history spans the 230 days the pass needs. `since` is `wantedAt`. A first try still stored live past its 20 minutes does not hold `waiting` back (the pass fails it and starts again), so its failed `lastRun` shows only once no due mark is left. A location whose first run the gate held, or one whose last try was within 24 hours, reads null until the pass actually starts a run, as a location with a published run always does. The pass can still be held by its 15 quiet minutes, the live cap, the weekly cap or a Monday part that ran out of time, so no `waiting` sentence states a time (decision 3). Under 230 days it is null, and no number is stated (14.1). The reference read runs only for a `not_calibrated` location with a mark. [CONFIRM: owners see a queued first forecast ("next") from the moment its history lands and the hourly pass will take it, and a running one ("building"); spec 14.1 and 14.2 gain build notes for both]

GET /api/org reads the newest calibration once per location, as it already reads coverage and the newest published run.

Words are client functions in `client/src/portal/upload/copy.ts` beside `calibrationHeading`, pure and pinned, with `formatTime` ("2:14 PM", the viewer's time zone) and `plural`; a `since` on an earlier day than the viewer's today adds the short date ("Sun, Nov 15, 11:58 PM"). "Building" is used only for `running`; no `waiting` sentence contains it or a time, and none promises that a forecast will be published (14.1). "First forecast" words follow the state: `not_calibrated` means no forecast now. While a refit runs, the stale line beside it drops “Townwise refits on {day} with the {n} days since.” for “The {n} days since aren’t in it yet.” (its `nextRefresh` null form), so the card and the overview tool never say the refit is both next Monday and happening now; “Forecast made from your sales through {day}.” stays. ### 4. A quiet poll, acting on done, and the last run

- `PortalProvider` gains `refreshOrg()`: it re-reads GET /api/org in place, keeping the ready org, the newest answer winning (`useRefreshable`'s rule). `reloadOrg()` is unchanged.
- `client/src/portal/hooks.ts` gains `useWhileRunning(running, refresh, { everyMs, onDone })`: while `running`, it calls `refresh` every `everyMs`, waits while the app is in the background (AppState, as `useImport`), waits 10 seconds after an error, and calls `onDone` once when `running` turns false after it was seen true in this mount (AiSection's `sawRunning`).
- The dashboard runs it on "any location updating", LocationShell on "this location updating", both with `refreshOrg` every 30 seconds. [CONFIRM: pages re-read every 30 seconds while a forecast is updating]
- On done, Home re-reads its forecast quietly (so the forecast replaces "Building" with no reload) and the model card re-reads its estimates. `onDone` shows no notice of its own. Home and the model card do not poll themselves (the location layout does): they watch for the end with `useWhenDone(running, onDone)`, the part of `useWhileRunning` that calls back, and re-read through `useRefreshable` (`src/portal/console/useRefreshable.ts`), which keeps what shows until the answer lands. `useWhileRunning`'s first re-read is `everyMs` after `running` turns true, not at once (the page has just read).
- **`lastRun`, a server fact.** On `not_calibrated` with `updating` null, `lastRun` is `{ outcome, reason, finishedAt }` from the newest calibration read above when it finished, or is live past its 20 minutes (then `not_run`, `failed`, dated `requestedAt` plus 20 minutes), through decision 6's `ownerOutcomeOf`; null when the location has none. For a succeeded one this reads its run by id (one read, only in this case). Home shows the not-published notice whenever the location is `not_calibrated`, not updating and has a `lastRun` that was not published, whether or not this mount saw the run (a `published` or `published_by_staff` last run on a `not_calibrated` location means every run since was withdrawn, so "wasn’t published" would be false and Home keeps its plain line): "The first forecast for {name} wasn’t published: {reason}" ({reason} is the clause of decision 7's first-forecast sentence after its "Not published:", `FIRST_FORECAST_REASONS` in `client/src/portal/upload/copy.ts`, which the history's words build on; `failed` reads "it couldn’t run."), then the next step, "Townwise tries again after your next sales upload." (none for `forecasts_off`, whose sentence says why), and a link "See what TownwiseAI did" to `?panel=activity`. The notice is plain words with no StatusTag (15.6): nothing runs until the next upload, so it carries no In progress tag, while the next, building and plain no-forecast lines keep theirs. A `waiting` that turns null without a run (the pass cleared an unchanged mark, refused the start, or staff paused it) leaves no `lastRun` of its own, so Home goes back to its plain no-forecast line, and the notice never points at an activity with nothing in it. [CONFIRM: Home's words and next step when a first forecast was not published]

### 5. What started it: `causes`

- The refit mark gains `refit.causes: Cause[]`, declared `{ type: [String], enum: CAUSES, default: undefined }` (the `refit.starts` precedent), set with `$addToSet` beside the `$max` on `wantedAt`. `locations.wantRefit(scope, locationId, at, cause)` and `wantRefitFor(ctx, scope, locationId, touched, cause)` take a required cause, so typecheck finds every caller. `clearRefitWanted` unsets `causes` in the same compare-and-set; a mark set after the pass read it moves `wantedAt`, the clear misses, and both stay.
- `Cause = 'weekly' | 'sales' | 'person_change' | 'townwise_ai'` for system starts:

| Caller | Cause |
|---|---|
| `handlers/sales.ts` `applyUpload` (the upload route and staff setup's), `files/worker.ts` (the file reader's days) | `sales` |
| `handlers/notes.ts`, `handlers/rules.ts`, `handlers/agent-changes.ts` (an undo), `handlers/data.ts` (undoing a file read) | `person_change` |
| `agent/apply.ts`, `files/ai-actions.ts` (an automatic read's days), `calendar/answers.ts` | `townwise_ai` |
| `lab/schedule.ts` `consider` (the weekly path) | `weekly` |

- `StartRequest` gains `causes`; `launch` passes them to `insertQueued`, which stores `causes` on a system calibration only when the list is non-empty, and omits the key otherwise. The calibration schema declares `causes` with `default: undefined` as well, so a person's start stores no `causes` key despite `minimize: false`. `considerRefit` reads the mark's causes with its `wantedAt` (`refitCandidates` answers them as a `RefitMark`, `RefitCandidate` plus `causes`, since the early-pass candidates share `RefitCandidate`); a mark from before this change has none, starts a refit with no `causes` key, and reads `unknown`.
- Person starts store none; their cause is read from `requestedBy.role`, whatever the `via`: `superadmin` reads `staff` ("Started by Townwise staff"), so a staff start through chat or a file read with the organization open as admin is never shown as the team's; `org_admin` reads `asked` ("Asked for by your team"). This keeps the privacy page's promise that org admins see every Townwise staff action on their organization.
- `sales` covers staff setup's upload too, so its words are neutral: "After new sales history was added", never "your upload".
- An older system calibration with no `causes` reads `unknown` ("Scheduled refresh"); no backfill and no join with `tw_forecast_weeks`.
- `via` does not change, so the staff console's `via` enum, `townwise.calibration_finished`, the infra test pins on it and the `forecasts_failed` alert (`via == "scheduled"`) are untouched.

Alternatives: new `via` values (break the console's strict enum and change what the alert catches); a single cause per mark (a burst of an upload and a note would lose one).

### 6. What it used, and the history

- `recordInput` (`lab/callback.ts`) also stores `dayCount` (the input's history days with guests, on or before its `dataThrough`: the input also holds the 400 days ahead, and a day with no row or one likely closed has no guests; a day with guests that a note or booking marks closed or booked still counts, though the lab leaves it out of training), `dataFrom` (its first day) and `newDays` (of those days, the ones after the `dataThrough` of the location's newest run with status `published` at the fetch, current or lapsed; null when there is none), all optional, absent on older records.
- `forecasts.firstPublished(scope, locationId)`: the location's run with the earliest `publishedAt` (any status, withdrawn included), as `{ runId, publishedAt } | null`. One rule for "first" in the history, the model card's history line and the email: a calibration's run is a first forecast when no run other than its own had a `publishedAt` at or before the calibration's `finishedAt`. A lapsed location (no run current, forecasts off or paused for weeks) is not "first". The history reads `firstPublished` once per request, so a calibration whose own run is the location's earliest published run reads as first even when another run was published before it finished; only a `not_judged` calibration (its run an older one Townwise already had) can be so, and its words are the same either way.
- `forecast_made` is appended to `ACTIVITY_SOURCES`. It reads `calibrations.list(scope, MAX_ACTIVITY, locationId)`, keeps finished ones and live ones past their 20 minutes (listed `not_run`, `failed`, dated `requestedAt` plus 20 minutes, read-only like `updating`), reads their runs' `status`, `publishedAt` and `publishedBy` in one batch by id (`forecasts.runStates(scope, runIds)`, at most 20), reads `firstPublished` once, and dates each by `finishedAt`:

```ts
{ at; kind: 'forecast_made'; calibrationId; causes: OwnerCause[]; outcome: 'published' | 'kept' | 'not_run';
  reason: OwnerReason; firstForecast: boolean; dayCount: number | null; firstDate: string | null;
  lastDate: string | null; newDays: number | null }
```

`OwnerCause` is decision 5's causes plus `asked`, `staff` and `unknown`. `ownerOutcomeOf(record, runState)` (decision 7) takes the outcome from what happened to the run, not only the gate:

- `failed` (or live past 20 minutes): `not_run`, the failure's reason.
- `succeeded` with `gate: null` (the run was not this calibration's draft: the same file as a run Townwise already had): `kept`, `not_judged`.
- the run has a `publishedAt`: `published`, reason `published` when the gate published it, `published_by_staff` when the gate held it and staff published it (`publishedBy` set).
- the gate published it but the run never got a `publishedAt` (staff withdrew or deleted the draft first, or it is gone): `kept`, `staff_withdrew`.
- otherwise: `kept`, the gate reason's owner reason.

No accuracy in the item: the outcome words say why, the model card already words the published run's accuracy in the owner's voice, and the activity GET is `member` policy while a draft's accuracy reaches only org admins (14.2's build note).

The merge keeps the newest 5 `forecast_made` items before the cut to 20, so a busy week of TownwiseAI changes does not push every run out. [CONFIRM: the history lists the newest finished runs among TownwiseAI's latest 20 activities, always keeping the newest 5 runs, failures included, with their causes and the days they used, and no accuracy]

### 7. Owner reasons and words

A new pure `api/src/lab/owner-outcome.ts` maps every `GateReason` and `CalibrationFailure` to a closed `OwnerReason` with an exhaustive `Record` (a new gate reason fails typecheck until mapped), and adds the run-derived reasons of decision 6:

No first-forecast sentence contains "current" or "didn’t change". No sentence states a minimum history (14.1) or promises a retry from the history (a cleared mark is not retried until new data arrives); Home's notice states the next step (decision 4). The line reads: outcome sentence, then the cause ("Weekly refresh", "After new sales history was added", "After your notes or rules changed", "After TownwiseAI’s changes", "Asked for by your team", "Started by Townwise staff", "Scheduled refresh"), then the days ("1,035 days, Jan 1, 2024 to Nov 15, 2026, 6 new"). The client's schema refuses a cause, reason or outcome it does not know, so such an item is left out like an unknown kind rather than worded wrong. The staff `GATE_WORDS` and `FAILURE_WORDS` stay staff-only. [CONFIRM: the owner reasons, their later-run and first-forecast words, and the cause words]

### 8. D7: no guest figure in any item

`forecast_made` and `lastRun` carry dates, counts and codes, never a guest or sales figure, for every caller. They are the same under view-as and open-as-admin, so `ActivityInput.caller` needs no `openAsAdmin`. This is stricter than D7 requires and is stated as its own rule, as D50 does.

### 9. The first-forecast email, once

### 10. The running-and-done pattern for D66

The pattern this change sets, which D66's research runs follow: (1) the read the page already makes gains an additive `{ stage, since } | null` field computed read-only, with a time limit read as not running and as a failed run; (2) the page polls with `useWhileRunning` and refreshes in place on done; (3) a finished run appends an activity kind with an outcome and codes, no figure, failures included, and the page links to it with `?panel=activity`; (4) the server decides the codes, the client the words.

Constraints D66 must meet, decided in its own design: a per-town run is shared by every organization in the town, so it lives in a non-tenant, town-keyed store holding public facts only, read by a location's tenant reads through an importer `api/test/isolation.test.ts` allows, never through `stores/cross-tenant.ts` from a tenant route; its progress reaches a location through GET /api/org's location summary (for example `research: { stage, since } | null`, covering the town's run and the location's own, with its own time limit); and its done item (`research_done`) is listed in each location's activity for its town's runs and its own. D66 adds its own kinds and field; this change adds neither.

## Risks / Trade-offs

- [`waiting` and the pass disagree] → `waiting` uses `refitCandidates`' own predicate and constant, `nextRefreshFor`'s conditions, the 230 days and the reference, so it never shows for a mark the pass will clear or skip for a day. The quiet 15 minutes, the live cap (an hour), the weekly cap (until the 7-day window frees, possibly days) and a Monday part that runs out of time can still delay a start, so the words say "soon" and state no time.
- [Polling load] → only while something updates, every 30 seconds, paused in the background; GET /api/org adds one indexed read per location, plus a reference read for a `not_calibrated` location with a mark and a run read for one with a succeeded last run.
- [A dead run reads updating] → read as not updating, and as a failed run, after 20 minutes, without a write.
- [Email to an admin who left] → only active seats with a user; a deleted user is skipped.
- [History pushes other activity out, or is pushed out] → at most one item a week per location from the weekly refresh, plus refits at most once a day; the newest 5 runs are always kept, and the rest of the newest 20 is shared.
- [Mixing owner and staff words] → separate maps, exhaustive by type.
- ["First" after every run was withdrawn] → the pages word by state, so a location whose every run staff withdrew reads "Building the first forecast" while the history and the email use `firstPublished` and do not call it first. Rare (a staff action) and left as is.

## Migration Plan

Optional fields only: `refit.causes` and `firstForecastMailedAt` on `tw_locations`; `causes`, `dayCount`, `dataFrom`, `newDays` on `tw_calibrations` (the strict schemas gain them, arrays with `default: undefined`). Refit marks pending at deploy carry no causes and start as before. No backfill. No index. No new collection, route or env var. Rollback: a client from before ignores `updating` and `lastRun` and drops `forecast_made`; an API from before omits them.
